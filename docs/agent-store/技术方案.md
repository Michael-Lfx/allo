## 1. 背景与核心问题

在构建面向桌面的本地优先（Local-first）自动化与智能体商店时，如果将业务层（产品、商店、会话、前端组件）与底层执行引擎（Nomi/Allo 执行器、底层 Actor、物理数据库）强耦合，系统将陷入以下严重缺陷：
1. **概念边界混淆**：把市场中展示的 Agent 资产误当做底层执行器，导致模型可以任意越权修改底层调度逻辑；
2. **多端接口分裂**：CLI、SDK 与 WebUI 各自调用私有 API 或直连 SQLite，造成行为漂移；
3. **安全凭据失控**：外部 MCP 连接器的 Token 与 API Key 散落在各个前端页面或消息上下文中，带来严重的凭据窃取隐患；
4. **长任务不可靠**：网络断线或宿主意外重启导致正在执行的长任务丢失状态或被伪造为成功。

## 3. 核心子系统详细技术设计

### 3.1 资产导入与不可变快照 (Importer & Catalog)
1. **多格式容错解包**：支持 CodeBuddy 插件包、技能市场与 MCP 连接器规范，对相对路径进行严格正则校验与 `canonicalize` 深度检测，拦截任何符号链接与 `..` 目录穿越逃逸。
2. **内容摘要与不可变快照（PluginSnapshot）**：导入成功后生成树级 SHA-256 摘要（`content_digest`），在数据库中建立不可变快照行。同一版本源重复导入自动命中复用（`reused=true`），内容篡改则标记为 `blocked`。
3. **三态兼容性评估（CompatTriple）**：输出包含语义兼容性、运行时可用性与分发许可状态的三维矩阵，不支持组件仅记录 Warn 说明，不阻断有效组件的正常安装。

### 3.2 运行时适配与协同编排 (Runtime Adapter & Team Orchestration)
1. **资产至内核的双轨映射**：
   - 商业层 `AgentDefinition` $\to$ 系统 `Preset` $\to$ 生成 `ResolvedPresetSnapshot`；
   - 运行时将 Snapshot 注入底层 `ExecutionParticipant`，最终驱动底层 `nomi` 执行器。
2. **多智能体协同（AgentTeam V1 方案）**：
   - **Leader 会话模式**：服务端自动拉起 Leader Conversation，由 Leader 在其首轮中调用 `nomi_delegate(strategy="planned")` 发起规划；
   - **Planning Context 隔离**：规划上下文仅包含 Leader 规划指令、Team 策略与脱敏后的成员能力摘要，严禁将成员私有 Prompt、内部 ID 或未经授权的工具细节混入全局上下文；
   - **DAG 依赖与局部并行**：调度器按拓扑序唤起无依赖的就绪步骤，并发数严格受限于 `max_parallel`。

### 3.3 统一公共 App Server 协议层
1. **双模传输与单分发点**：
   - WebSocket 承载长连接全双工交互、流式事件推送与审批回调；
   - HTTP 端点处理无状态单次调用（导入、上传）；
   - 双端共用底层同一分发器（`dispatch_connection_request`），保障语义 100% 同构。
2. **契约指纹守门**：引入单调自增计数器 `fp-<n>`（当前 `fp-12`），握手阶段严格比对，消解多版本并行的维护泥潭。
3. **完全 Opaque ID 体系**：对外抹除一切内部数据库主键与系统路径，仅输出全局唯一 UUIDv7（`run_id`、`session_id`、`workspace_id`）。

### 3.4 连接器沙箱与凭据安全管理
1. **凭据零过线原则**：API Key、OAuth 令牌、物理私钥严格保存在宿主安全存储中，绝不出现在 Prompt、事件流、终端响应或日志中。
2. **模板即声明规范**：连接器配置中通过 `${secret:KEY}` 声明凭据需求，调用时由宿主受控代理（`connector/call`）在内存中解析并转发，调用方无法直接触碰原始凭据。
3. **标准 OAuth PKCE 闭环**：支持回环重定向、内存存储、401 静默刷新与单次幂等重试。

### 3.5 运行事实与崩溃自愈
1. **Event Log 唯一事实源**：任务执行过程产生的规范点号事件（如 `run.started`、`step.completed`）由服务端分配物理自增序号 `sequence` 并持久化。
2. **硬杀崩溃恢复**：系统重启后调度器主动执行扫描，对于未决 Attempt，若无法严格证明外部操作安全性，统一标记为 `recovery_required`，绝对禁止向前端伪装为 `completed`。

## 4. 关键架构决策与权衡矩阵

| 决策点 | 备选方案 A | 备选方案 B | 最终决策 | 决策依据与权衡 |
| :--- | :--- | :--- | :--- | :--- |
| **执行引擎选型** | 同时支持接入外部多种异构 Agent 引擎 | 确立 Allo/Nomi 为系统唯一的执行引擎 | **方案 B** | 多引擎会导致事务一致性、状态机持久化与断线自愈能力无法收敛；单一内核保证了架构的高内聚与可信赖度。 |
| **资产与运行时解耦** | 将智能体定义直接作为运行时 Actor 注入 | 资产定义解耦为静态 Preset，动态实例化为 Snapshot | **方案 B** | 静态资产具有版本不可变性与交易属性，运行时需要状态与上下文隔离，双轨映射保障了资产升级时正在运行的任务不受破坏。 |
| **Team 编排机制** | 允许模型自由直连发消息与自主认领任务 | 基于 Leader Planning Context 驱动的 planned DAG | **方案 B** | 自由网状通信极易造成死锁、死循环与不可控的 Token 消耗；确定性的 DAG 拓扑具有完全的可解释性与可控性。 |
| **外部连接器接入** | 允许外部脚本直接执行 Shell 命令连接 MCP | 宿主提供受控子进程沙箱与调用代理（connector/call） | **方案 B** | 彻底防范恶意代码注入与凭据窃取，保障操作审计与资源超时强制回收。 |

## 1. 文档定位

### 核心术语原则（必须遵守）

Agent Store 的 Agent 是产品层定义，在 allo 中通过 Preset 机制承载；nomifun 的 Agent 才是 Claude Code、Codex 这类实际执行 Runtime。Runtime Adapter 的职责是把前者解析为 `ResolvedPresetSnapshot` 并写入 `ExecutionParticipant.preset_snapshot`，再交由 Runtime Agent/Driver 执行。

当前 App Server Runtime Spike 将入口收窄为 `builtin-office` Preset + `agent_type=nomi`；ACP Runtime 继续保留在 allo 原有会话路径，不从该入口运行。

本文是开发实施的技术总方案，不替代领域模型、Protocol、安全和测试主表。公共状态、事件、planning、错误码和幂等字段以 `10-public-contracts.md` 为准；测试用例以 `agent-store-v1-test-cases.md` 为准。

本文中的“支持”分为三种：

```text
设计支持：规格已定义，但尚未有运行证据
Runtime verified：已通过真实 allo 链路测试
Release eligible：已通过发布门禁并允许对外启用
```

当前整体仍属于设计支持，不能将本文作为已实现能力声明。

## 2. 技术目标

V1 必须形成以下本地优先闭环：

```text
CodeBuddy/WorkBuddy Importer
    → PluginSnapshot / Catalog
    → AgentDefinition/Team/Skill/Connector Definition
    → Preset/ResolvedPresetSnapshot
    → Runtime Adapter
    → allo Runtime Agent/Driver
    → Event Log / Projection
    → App Server Protocol
    → TypeScript SDK / CLI / Web/Flowy
```

核心交付：

- 单 Agent 可执行 Run；
- 固定成员 AgentTeam；
- Leader Planning Context 驱动的 `planned` DAG；
- ready Step 局部并行；
- retry、replan、Event、Artifact；
- Connector 工具策略和标准 OAuth 子集；
- App Server 是所有外部客户端的唯一公共边界。

## 3. 非目标

V1 不实现：

```text
第二个 Runtime
完整 Mailbox
成员自主认领
成员长期独立会话
成员任意直连消息
嵌套 Team
任意 Hook/bin/script 执行
完整 LSP Runtime
复杂 OAuth 变体
云端执行、多租户、HA、灾备
```

这些能力只能作为明确的 `unsupported`、`manual-review` 或 deferred capability 暴露，不能让客户端看到“已支持但运行时失败”。

## 5. 模块职责

### 5.1 Importer

输入：

```text
.codebuddy-plugin/plugin.json
.codebuddy-skill/marketplace.json
.codebuddy-connector/connectors.json
组件目录和依赖
```

职责：

- 校验相对路径、路径遍历和符号链接逃逸；
- 复制到版本化不可变缓存；
- 计算 content digest；
- 解析 Agent、Team、Skill、Connector、Command、Hook、LSP 和 CredentialSchema；
- 保留来源、版本、依赖和未支持组件；
- 生成 CompatibilityReport。

Importer 不直接创建 allo `AgentExecutionTemplate`。

### 5.2 Catalog

Catalog 保存：

```text
PluginSnapshot
AgentDefinition（Agent Store Agent）
AgentTeamDefinition
SkillDefinition
ConnectorDefinition
CompatibilityReport
版本、来源、digest、启用状态
```

来源内容发生变化必须生成新 Snapshot，历史 Definition 不原地修改。

### 5.3 Runtime Adapter

Adapter 是唯一的领域模型到 allo 内部对象的边界。Team V1 采用模式 A：Leader 是规划角色，Runtime Adapter 根据 Leader Preset 指令、Team 目标、脱敏成员能力摘要和 Team 策略构造一次性的 Planning Context，交给内部 Planner；不创建独立的 Leader Conversation，也不依赖 `nomi_delegate` 工具。成员完整 persona、Skill、Connector 和 Tool Policy 仍分别绑定到各自 Participant Snapshot。

Planning Context 是运行时派生输入，不是新的产品定义。它只能包含规划所需的 Leader 规划指令、Team 策略和脱敏成员能力摘要；不得包含成员完整 Prompt、真实凭据、凭据值、未授权工具细节或 allo 内部 ID。可对其规范化内容计算 digest，供运行审计和复现。


```text
AgentDefinition
    → allo Preset/ResolvedPresetSnapshot
    → ExecutionParticipant.preset_snapshot
    → nomifun Runtime Agent/Driver
    → Agent Run

AgentTeamDefinition
    → 分别解析 Leader 与成员的 Preset/ResolvedPresetSnapshot
    → AgentExecutionTemplate / 固定 Participant 池
    → Planning Context（Leader 规划指令 + 脱敏成员能力摘要 + Team 策略）
    → 内部 Planner 生成 planned DAG
    → Step/Attempt 使用各自 Participant Snapshot 执行
```

Adapter 不向公共协议暴露 allo 内部 ID、数据库对象或私有事件。

### 5.4 App Server

App Server 负责：

- AuthContext 建立和权限校验；
- Command、幂等和版本检查；
- Catalog、Thread、Run、Event、Artifact、Approval、Connector API；
- 公共 ID 和错误码映射；
- Run/Event 持久化状态查询和 Server Request；
- 不让 SDK、CLI、Web 直接访问 allo 私有接口。

### 5.5 Connector Manager

Connector Manager 负责：

- 工具发现、命名空间和 allowlist；
- CredentialBinding 引用解析；
- 请求时 Token 注入；
- issuer/resource 校验；
- 401 刷新和单次重试；
- Probe 和连接状态；
- Tool Policy、Approval 和审计。

真实凭据只能进入本地安全存储和受控 transport，不进入 Prompt、Event、Artifact、Renderer 或公共 API。

## 6. 数据与持久化设计

### 6.1 不可变对象

```text
PluginSnapshot
Definition version
Execution Snapshot
AgentExecutionTemplate snapshot
CredentialSchema
```

Run 创建时冻结：

```text
AgentDefinition/PluginSnapshot digest
Preset revision/digest
Skill versions
Connector policy
Participant configuration
Planning limits
Workspace reference
```

### 6.2 运行事实和投影

```text
Client Command
    → Auth/Policy validation
    → Idempotency Intent
    → allo execution
    → append canonical Event
    → update Projection
    → response / notification
```

唯一事实来源：

```text
Event Log
```

可重建投影：

```text
Run
PlanRevision
Step
Attempt
Approval
Artifact index
```

必须满足：

- 事件序号（sequence）由服务端分配；
- Run/Step/Attempt 状态以持久化快照为准；V1 不要求从事件重放重建；
- allo 引擎内部既有的版本/CAS、lease/fencing 与 receipt 保护继续生效，但不作为公共契约承诺；
- 迟到写入不能覆盖新状态与终态；
- 事件和终态不能因进程退出而静默丢失。

### 6.3 V1 重启策略

V1 启动时复用 allo 既有恢复扫描：根据 queued/running Attempt、receipt 和内部 lease/CAS 结果继续处理；无法证明外部效果安全时保持 `recovery_required`，不得把进程退出伪装成 completed。App Server 不对外承诺原 Attempt 一定续跑；用户显式重跑时创建新的 Run/Attempt，并使用外部幂等键或人工确认。

恢复操作的公共协议、跨 Run 事件追平和服务端恢复策略配置列为 V2；allo 内部 Intent、投影 CAS、Attempt fencing、receipt 和恢复扫描继续作为 V1 Runtime 安全机制。

## 7. AgentTeam V1 执行流程

```text
1. 校验 TeamDefinition、版本、权限和 Connector Binding
2. 分别解析 Leader 和成员的 Preset/ResolvedPresetSnapshot
3. 创建 AgentExecutionTemplate 和固定 Participant Pool
4. 构造 Planning Context（Leader 规划指令 + 脱敏成员能力摘要 + Team 策略）
5. 调用内部 Planner 生成 PlanRevision
6. 校验依赖、成员路由、策略和 max_parallel
7. Materializer 生成 Step
8. 调度 ready Step
9. 运行 Attempt，并使用对应 Participant 的 Prompt Snapshot
10. 写入规范 Event
11. 失败时 retry 或生成新 PlanRevision
12. 汇总 Artifact 和 TeamRun 结果
```

V1 不允许模型动态增加 Team 外成员、绕过 routing constraint、把成员完整 Prompt 直接共享给其他成员，或用顶层 `parallel` 替代 Team planned 流程。`nomi_delegate` 仅是普通可信会话的委派能力，不是 TeamRun 的必要入口。

## 9. 安全控制

权限计算：

```text
caller ∩ agent ∩ team ∩ skill ∩ connector ∩ credential scopes
```

默认需要 Approval 的操作：

```text
发送、发布、删除、修改外部记录、部署、支付、任意命令、越界文件写入
```

V1 默认：

- Hook/bin/script 只静态导入，不自动执行；
- CLI 使用命令白名单、参数 Schema、工作目录和环境变量 allowlist；
- STDIO MCP 使用受控子进程、超时、退出回收和审计；
- Artifact 绑定 Run/Workspace，不允许任意本地路径读取；
- Renderer 不访问凭据、MCP、stdio 或安全存储。

## 10. Runtime Readiness Gate

```text
model-defined
    → adapter-defined
    → runtime-verified
    → release-eligible
```

单 Agent 必须先通过：

```text
Preset/ResolvedPresetSnapshot
→ ExecutionParticipant.preset_snapshot
→ Runtime Agent/Driver
→ Run → Event → Result
```

再验证：

```text
Event Log / Projection / Recovery
```

最后验证：

```text
Credential Provider / Transport injection / Probe / 401 retry
```

Team、SDK、Web 不得绕过该顺序宣称端到端完成。

## 11. 技术约束与实现原则

- allo 是唯一 Runtime；不得引入第二个执行引擎；
- App Server Protocol 是唯一公共边界；
- 公共 ID 必须 opaque；
- 运行时只读不可变 Snapshot，不读来源目录；
- 公共 JSON 使用 snake_case，TypeScript 使用 camelCase 映射；
- Protocol 类型应由 Schema 生成，SDK 不手工维护第二套公共枚举；
- 外部副作用必须具备策略、审批、审计和幂等语义；
- 不把设计存在、类型存在或登录成功当作运行能力证据。
