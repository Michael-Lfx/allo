# 故障复盘与经验教训：v1.4.9 生产版本硬编码测试积分 Mock 数据泄漏事故

- **事故日期：** 2026-09-24 ~ 2026-09-25
- **事故级别：** P1 / 核心资产展示异常与全局错误阻断
- **影响版本：** `v1.4.9`
- **修复版本：** `v1.5.0`（Commit `531813ff8`）
- **报告编写人：** Flowy Team

## 一、事故概要

在 2026-09-25 发布的 `v1.4.9` 版本中，用户登录客户端后发现：**无论其实际账户拥有多少积分，侧边栏账户区均强制展示为 500 积分，并且全局常驻弹出“积分即将耗尽，当前积分低于 1,000，建议及时补充以保障对话连续性”的警告气泡**。

经紧急排查，该事故根因在于此前为了测试积分不足气泡的视觉动效，在 `CreditsContext.tsx` 中写入了作为默认兜底状态的 Mock 代码 `{ balance: 500, authenticated: true }`，且该代码被直接带入主干分支并随 `v1.4.9` 一并打包发布，完全覆盖了从后端 IPC 获取的真实用户积分。

## 三、根本原因分析 (5 Whys Root Cause Analysis)

1. **为什么用户在生产环境看到的积分恒为 500，且一直误报积分耗尽气泡？**
   - 因为 `CreditsContext.tsx` 中导出的 `balance` 被 `effectiveBalance` 强行替换成了 `mockCredits.balance`（500），而 500 小于设定的告警阈值 1,000。
2. **为什么 `mockCredits` 会在生产环境下生效？**
   - 因为组件的 `useState` 初始化函数中存在一段无防护的兜底逻辑：
     ```tsx
     const [mockCredits, setMockCreditsState] = useState(() => {
       const loaded = loadMockCredits();
       if (loaded !== null) return loaded;
       return { balance: 500, authenticated: true }; // <--- 硬编码兜底！
     });
     ```
     在没有本地存储配置时，它默认无条件返回 500，且没有任何环境变量或调试开关守卫。
3. **为什么要在业务核心 Context 中直接写入写死的数据？**
   - 开发者为了“快速在界面上调试气泡”，图一时便利直接改动了最底层的真实状态机，而没有采用页面外部传参、Storybook 预览或单测 Mock 等规范解耦方案。
4. **为什么在 PR 合并前的多轮 Code Review 中没有发现？**
   - **审查关注点偏移：** 后续迭代中，注意力完全集中在“明暗色对比度”、“图标和文字间距”、“吸顶背景不透明度”、“工作区折叠竞争死循环”等高感知复杂问题上，潜意识中默认底层的“积分上下文已跑通”，造成了审查盲区。
   - **测试代码造成了“假安全”幻觉：** 当时为该 Mock 功能补充了存储读写的单元测试，跑测试时全部绿灯，掩盖了它覆盖生产数据流的致命隐患。
5. **为什么在发布版本前未能被拦截？**
   - **静态门禁缺失：** 现有的 `bun run check` 质量门禁包含语法检查、i18n、主题、进程边界等，但没有针对生产代码中出现 `MOCK_`、`__setMock` 或硬编码资产数据的拦截规则。
   - **发版前缺乏冒烟测试：** 发版打包后未在真实生产网络环境中用真实账号进行一轮基础核心功能（冒烟测试）验证。

## 四、经验教训 (Lessons Learned)

1. **业务全局状态严禁侵入任何默认 Mock 数据**
   - 核心资产、认证、网络层 Context 必须保持 100% 纯净，严禁为了“本地肉眼看效果”而在业务代码里直接写死初始值。
   - 调试 UI 的正确做法：
     - 利用可交互预览文档（如已建立的预览 HTML / Storybook / 独立 Demo 页面）；
     - 或者仅在特定沙盒路由（如 `/#/test/...`）且明确限定 `import.meta.env.DEV` 时由外部注入，绝不污染全局 Context。

2. **关注点转移（Attention Drift）是审查的最大敌人**
   - 当一个 PR 反复修改了多个不相关的模块（如从气泡逻辑修到了侧栏 CSS、再修到工作区列表的 useEffect），极容易让审查者产生疲劳，漏掉最早期提交的代码隐患。
   - **原则：** 涉及 Context / 全局状态的改动，必须独立成小 PR，严禁与普通 UI 样式调整混合提交。

3. **防御性设计：必须考虑升级用户的本地残留**
   - 当发现代码可能已在本地写入测试数据（如 `nomifun:credits:mockBalance`）时，修复方案不仅要删除功能，还必须**主动清理本地缓存**，否则升级上来的老用户可能仍然被历史脏数据影响。
