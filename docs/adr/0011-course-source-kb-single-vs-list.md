# ADR-0011: 来源库的单列/列表双读——列表为主，单列是兼容位

Status: Accepted

Date: 2026-10-13

## Context

多知识库建课（t4）在迁移 073 给 `learning_courses` 加了 `source_kb_ids`
（JSON 数组，**首个元素 = 主来源**），同时**保留**了迁移 015 的单列
`source_kb_id` 及其 SetNull 契约与索引。课时侧同理（迁移 075 的
`learning_lessons.source_paths_json` 配迁移 015 的
`source_path`/`source_start`/`source_end` 三列）。于是读侧出现一个必须显式
决策的形态：**两列都在，读谁、写谁、谁退役**。

背景约束（不可回避的三个事实）：

1. `source_kb_id` 是 v3 逻辑引用契约的登记列（`id_schema_contract.rs` 的
   `text_ref!`，SetNull + RequireParent）：删库时孤儿审计要求它可被修复流程
   置空，索引 `idx_learning_courses_source_kb_id` 与既有的按库反查也在用。
2. 老行（描述流课程、t4 之前的课程）只有单列/三列——任何读侧口径都不能让
   它们失效或读出不同的课程。
3. 列表是**新增能力**的载体：多库建课的采样命名空间、逐库披露、课时多引用
   都靠它承载，读侧还必须把已删库的 id 过滤掉（迁移 073 的裁决：库里可以
   残留悬空 id，但**不外泄**）。

## Decision

**列表列是事实来源，单列/三列是它的兼容位；两者不退役，读侧一律"列表优先、
过滤已删库、空则回退兼容位"。**

- **写侧**：新建课程只写列表（`source_kb_ids`），单列由应用层同步为列表首个
  （`import_course_with_context`：`primary_kb_id = source_kb_ids.first()`）。
  列表唯一新增空位时（单库请求）退化为单元素列表，单列同值——单库路径与
  历史形状逐字一致。课时侧同理：`source_paths_json` 写全量引用，三列写首个。
- **读侧**：`CourseKbSources`（`source/course.rs`）把列表解析为库 id 列表，
  再按现存库集合过滤；主来源 = **过滤后**首个（`source_kb_id` 的 SetNull
  语义由应用层承担）。列表为空（老行/未回填）回退单列的单元素视图。课时
  视图逐条解析引用清单，同样过滤已删库、路径保持原样（前端如实报错）。
- **已删库的归属**：不过滤就外泄悬空 id（契约纪律），过滤后必须保证"绝不把
  未知前缀的路径认给幸存库"——解析不到存活库 = 无实时来源，走快照兜底
  （t4 评审修复；`service/lesson.rs` 的 `assemble_lesson_grounding`）。
- **列表列参与逻辑引用契约**：迁移 073 的列表在 `id_schema_contract.rs` 里
  按 `cs_agents.knowledge_base_ids` 先例登记（迁移 074 补具名索引），
  口径 `KeepHistory` + `AllowMissingHistoricalParent`——已删库 id 允许留在
  历史行里、由读侧过滤；单列的 SetNull 登记保持不动（两列各按自己的语义
  被审计与修复）。
- **不退役单列/三列的理由**：它是 v3 契约的登记列（SetNull 修复语义、索引、
  按库反查），退役要动契约与迁移回滚面；它同时是"未被 t4 覆盖的读侧/导出
  面"（教程播种、备份/恢复、旧客户端）的唯一来源。代价见下。

## Considered Options

- **只留列表、退役单列**：读写口径最干净，但要改契约登记、删索引、重写所有
  按库反查的 SQL、并为备份/恢复与教程播种改口径——收益（少一列）不抵
  回归面（t4 的"零回归"要求）。
- **只留单列、列表只当展示元数据**：多库的主来源无法表达（单列只有一个
  id），采样命名空间与逐库披露失去事实源，等于放弃 t4。
- **读侧不做过滤（列表原样外泄）**：违反 v3 的"不外泄悬空 id"纪律，
  前端会拿到已删库 id 去读文件（悬空归属）。
- **两列同时写、读侧二选一（现状之外的口径漂移）**：任何"有时读单列"的
  分支都会让同一行在不同代码路径上给出不同主来源——本 ADR 明确：**只有
  列表为空时才读单列**，一条件，无第二处判断。

## Consequences

- 同一行数据存在冗余（单列 = 列表首个），写侧必须**成对维护**：新增写路径
  （导入、迁移回填、将来任何编辑面）要么同时写两列，要么不碰单列（只写
  列表会破坏"主来源 = 单列"的旧读侧假设）。当前写点只有 `import_course_with_context`
  一处（课程）与课时导入一处，都成对写。
- 修复流程的孤儿审计对两列各报各的：单列被 SetNull 修复置空、列表由读侧
  过滤——两者的处置不同是**设计**（单列是契约行、列表是历史能力），
  不是不一致；`AuditFinding` 里两列会同时出现（列名带 JSON 路径）。
- 读侧多一步过滤（每课程一次 `existing_knowledge_base_ids`），代价是一次
  小查询；换来的是"删库后课程仍可读"的确定语义（t4 验收钉子：删其一 →
  该课时走快照、不读成幸存库的文档）。
- 后端 DTO 同时给 `source_kb_id`（首个现存库，兼容）与 `source_kb_ids`
  （过滤后列表），前端只用后者做披露、用前者做"知识来源"按钮目标——
  TS 镜像（`ui/src/renderer/pages/learning/types.ts`）与 Rust 结构同形。
- 后续若要退役单列，前置条件是：备份/恢复、教程播种、旧客户端读面全部改
  读列表，并同步更新 `id_schema_contract.rs` 的登记与迁移索引——届时本 ADR
  需要一份后继 ADR（不是修改本文件）。
