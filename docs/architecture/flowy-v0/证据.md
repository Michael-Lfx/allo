### 11.1 参照实现的历史增长实测（AutoLoop，Apple M5 Pro，**不是我们的数据**）

**四条要记住的**

1. **热路径恒定** —— 领活 0.82–0.89 ms，与历史无关。靠的是索引，不是常驻内存（空闲 RSS 一直 59 MB）。
2. **汇总线性变慢** —— 11.2 → 83.6 → 927 ms。凡是「遍历历史做统计」的接口都会这样，要么分页要么预聚合。
3. **格式变更的代价是秒级停机** —— 110 万条全量重建 43.1 秒、峰值 141 MB。平时重启不重放。
4. **磁盘只增不减** —— 日志只追加不压缩，必须自带保留策略。

它的测量口径也值得抄：**不通过改变采样时间或主动触发 GC 来降低读数。**

### 11.7 两条硬规则的实测：方案失败（2026-11-23）

> ⚠️ **本节的结论只适用于「程序化决策」，不适用于「程序化校验」。**
> 两者必须分开：校验判错会变红（可见），决策判错会被静默吞掉。
> 设计侧的正确表述见 `最终方案.md` §6.3。



§11.6 提出用两条程序规则收敛方差。**实测证伪，两条都该删。**

| | 纯 Judge（§11.6） | 加两条规则（本节） |
| --- | --- | --- |
| 准确率 | 8~10 / 10 | **7 / 10 × 三次** |
| 三次一致性 | 3 种 | **2 种** |

#### 规则一错在哪

「明天要，急」—— 无 work 关键词、无动作词 → 判成 `chat_only`。

正确答案是 `ask_human`：用户在催某件事，只是没说哪件。

**而 `chat_only` 不出卡、不打扰。这条消息被静默吞掉了。**

#### 规则二错在哪

「再细一点」本该问人。但规则二发现上一条已归属 work_001、本条 <10 字、无独立对象词 → **继承成 work_001**。

同样静默。

#### 更根本的：规则一的「覆盖」是假的

规则一能判对「汇报里把华东改成华南区」，靠的是一张**我按测试集手工写的关键词表**——我把「标题」塞给了 work_001。

**但 Judge 看不到这张表**，所以它在「标题改成季度经营回顾」上判 `ask_human`。**Judge 其实更诚实**：三个 work 的 brief 里都没出现「标题」。

**用测试集拟合出来的人工表，测出来的是表的覆盖率，不是系统的能力。**

#### 结论：方向错了

我原以为「用程序消除歧义」。实际上程序消除的不是歧义，是**可见性**。

| | 判错之后 |
| --- | --- |
| Judge 判错 | 出卡，你一眼看到归属，点一下就能改 |
| 程序规则判错 | **静默消化，你根本不知道它丢了** |

**所以正确的方向不是「把判断搬进程序」，而是「让判断的结果可见」。**

#### 修正

1. **快筛只保留一条**：含「另外 / 还有个 / 新的」→ `new_job`。这个词是强信号，确定性极高。
2. **删掉「0 关键词 → chat_only / ask_human」** —— 它是 p7、p10 两处错误的来源。
3. **删掉批内继承** —— 它把「再细一点」静默塞进了汇报。
4. **回到纯 Judge ＋ 回显 ＋ 一键改 ＋ 批量确认**。

**一句话：宁可让模型猜错并且说出来，也不要用程序判对却不说。**

### 11.6 三轮对比：稳定性到底取决于什么（2026-11-23）

| 实验 | 题库 | 准确率 | `ask_human` 率 | 三次一致性 |
| --- | --- | --- | --- | --- |
| 1 | 6 条，2 条模糊 | 4/6 · 5/6 | — | 各自内部完全一致 |
| 2 | 8 条全模糊 | 6/8 · 6/8 · 4/8 | 62% · 62% · 12% | 2 种 |
| 3 | 10 条，4 条模糊 | 10/10 · 8/10 · 10/10 | 30% · 10% · 40% | **3 种全不同** |

#### 一致性为什么一轮比一轮差

**不是随机抖动，是规则里留了真实的歧义空间。**

判定规则第 4 条写的是「实在判不出来 → `ask_human`」。**但没定义什么叫「实在判不出来」。**

于是同一个模型在两种理解之间摇摆：

1. **保守理解** —— 只要缺指代对象就问人 → `ask_human` 率 40%~62%
2. **激进理解** —— 能挂上某个 work 就挂，连续消息还往后继承 → `ask_human` 率 10%

实验 3 里的第二次运行就走了第二条：它把「用红色」「明天要急」**继承**给了上一条的 work_001，理由是「承接同比列」。

#### 所以修正 §11.5 的建议

§11.5 说「Judge 必须 temperature=0」。**不够。** temperature=0 只能减少抖动，消除不了歧义。

真正的解法是**把「判不出来」从感觉变成计数** —— 这正是 DSH 两级过滤的思路：**能用程序判的，别问模型。**

#### 两条可以直接写成代码的规则

1. **快筛加一条**：消息里**没有匹配任何 work 的关键词**（brief 里的名词／动词表）→ 直接 `ask_human`，不进 Judge。
2. **批内继承显式化**：若上一条已归属 `work_X`，且本条**少于 10 字、无独立主语** → 继承 `work_X`；否则独立判断。

> ⚠️ **这两条实测证伪了，见 §11.7。** 不要实现。

两条都不依赖模型，而且正好覆盖实验里分歧最大的那几条（「加一列同比」「用红色」「明天要急」）。

#### 一句总结

**Judge 的稳定性不取决于题目难度，取决于规则有没有留下解释空间。**
留下一个「实在判不出来」，就会长出两种天气。

### 11.5 Judge 会不会说「我判不出来」（2026-11-23）

**假设被证伪。** 我原以为 Judge 宁可硬猜也不肯用 `ask_human`。实测不是——它不但会用，还会用得很凶。

**题库**：8 条缺指代对象的消息（「再细一点」「改成红色」「明天要用，加急」…）。快照按 §11.4 的结论中性化，跑 3 次。

| | A | B | C |
| --- | --- | --- | --- |
| 准确率 | 6/8 | 6/8 | **4/8** |
| `ask_human` 次数 | 5 | 5 | **1** |
| `continue_job` 次数 | 1 | 1 | **4** |

**A 和 B 逐字节一致，C 的行为模式整个换了。同一份快照、同一套规则。**

#### 这条推翻了 §11.4 的一条结论

§11.4 写「可复现性成立」。**不成立。**

上一轮 5 次全一致，是因为那批题目区分度高；这批模糊题上，一致性只有 2:1。

**而且分歧不是随机的，是模式级的**：

1. **A/B 走保守路** —— 判不出来就问人（5/8）。
2. **C 走激进路** —— 硬塞给已有 work（4 条 `continue_job`）。

#### 三条修正

1. **Judge 必须固定 temperature=0。** 不固定就不能承诺任何可复现性。**这是实现约束，不是设计选择。**
2. **`ask_human` 会带来打断洪水。** A/B 在 8 条里问了 5 次。所以要能**批量确认**——一次列全，而不是一条一问。
3. **`chat_only` 的语义要写死。** 「现在到哪了？」在 A/B 被判成 `ask_human`、在 C 判成 `chat_only`——因为文档没说清：**这类问题根本不需要归属**，Router 自己有全局状态就能答。

#### 一个新发现的误判模式：「重复即延续」

「按部门拆分」三票全判给预算表，理由是「预算表本就按部门拆分」。

**它把用户的话当成对已有 brief 的复述，而不是新指令。** 而真实场景里，用户是在说「这次要按部门拆分」——可能指的是汇报。

这个模式要进失败模式清单。

#### 顺带一条

即使 Judge 判对了，也只有 6/8。**这再次说明「回显 ＋ 一键改 ＋ 批量确认」不是锦上添花。**

### 11.3a 端到端骨架跑通（2026-11-23）

`flowy-skeleton/` 把链路串起来跑了一次。**11 个事件，从消息到签字。**

**真的部分**：能力包脚本（`render.py` / `check.py`）、核验四码、sha256 签字、事件日志。

**假的部分**：Judge（剧本字典）、交付外发（mock 四态）。**这个骨架验的是系统集成，不是模型能力。**

#### 跑出来的数字

| 环节 | 结果 |
| --- | --- |
| 渲染 | `deck.pptx` 约 31 KB / 270~420 ms |
| 核验 | `ok=True fields=12 issues=0` |
| 故障注入（改 F01 的值） | `ok=False`，`VALUE_MISMATCH` × 3（F01 / F05 / F09） |
| 自动重做 | 重做后 `ok=True`，继续到签字 |
| 签字哈希 | `status` 拿当前文件重算，显示「一致」 |
| 状态重建 | 只读 11 条事件，不读内存 |

#### 并发：Router 会不会被 Worker 堵住

三个 work 同时跑，Worker 里塞 2.5 s 慢工具；期间连发 5 条消息，**每次判归属模拟 600 ms 模型耗时**。

| 指标 | 数值 |
| --- | --- |
| 三次派活 | **2 ms** |
| Worker 各自用时 | 2.75 s × 3（并行，不是 8.25 s） |
| Router 处理 5 条 | 3.00 s |
| 整轮墙钟 | **4.01 s** |
| 若两者串行 | 5.75 s |

**关键不是 Router 快，是 Router 不在 Worker 的 await 链上。** 这就是 §5.1 说的「两个 loop 实例」在代码里的样子。

> 第一次跑时 Router 延迟只有 0.02 ms —— 因为 Judge 是字典查找，那个数字什么都证明不了。
> 给每次判定加了 600 ms 模拟模型耗时之后，才成为一次真正的验证。**测一个东西之前，先问它会不会自己骗自己。**

#### 打断：kill 之后必须确认

派一个会跑 200 秒、每秒吐 100 行的工具，0.8 秒后点「停」。

| 指标 | 数值 |
| --- | --- |
| 0.8 s 内收到 | stdout **73 行** / stderr **25 行**（并发读，无死锁） |
| `kill()` 返回耗时 | 5.62 ms |
| **`kill()` 返回那一刻 `poll()`** | **`None` —— 进程还活着** |
| 轮询确认 | 2 次 / **17.8 ms** 后 `poll() = 1` |
| 最终状态 | `closed_aborted` |

**最有价值的是第三行。** `kill()` 只是发信号，返回时进程还活着。如果那 17.8 ms 里就放开槽位、派新活，
两个进程会同时读写同一批文件。

**顺序铁律：`kill` → 轮询确认 → 才改状态 → 才放开槽位。** 这条现在有数字了。

事件链是完整的：`work_open → attempt_start → abort_requested → abort_confirmed → abort_settled → work_close(aborted)`。
`status` 从这 6 条事件重建出 `closed_aborted`，不读内存。

#### Judge 接真模型：在线跑通了

`FLOWY_JUDGE` 可切 `script` / `file` / `cmd` / **`http`**。`http` 后端已实测。

| 指标 | 数值 |
| --- | --- |
| 单次判定耗时 | **803 ms**（另一次 1817 ms，含 120 推理 token） |
| token | 154 输入 + 76 输出 |
| `temperature` | **0**（§2.5 的实测约束） |
| 判定 | `continue_job / work_001`，理由「与现有季度汇报任务一致」 |

**理由的措辞就是证据**：真模型说「与现有季度汇报任务一致」，剧本说「唯一匹配 work_001 的简报」。
同一结论、不同的话 —— 判定确实来自模型。链路照常走完 11 个事件到签字交付。

**Key 只走环境变量，不落盘。** 交接目录里搜不到任何 key 字符串。

**之前为什么接不上**：`dsh headless` 报 `MISSING_CREDENTIAL`，
`.credentials.yaml` 里只有 Gemini / opencode-go / 星驰，没有 DeepSeek。
换用户给的 OpenAI 兼容网关后直接通了 —— **卡住的从来不是代码，是 key。**

#### 五条被证明的

1. **数据结构能串起来** —— 一条消息从进来到签字，中间没有断点。
2. **核验真能拦住错** —— 改一个值，立刻报出字段 id。
3. **签字可验证** —— 重算 sha256 能和签字记录对上。
4. **状态可重建** —— `status` 只读日志。
5. **分支能走** —— 值不对自动重做，重做还不成才交给人。

#### 一条没证明的

1. **没有真外发**。

#### 顺带一个教训

第一次做故障注入时，我按 `slides[].value` 去改，而配方真实结构是 `pages[].text`。

**代码静默什么都没改，链路照样「通过」了。**

这正是 §11.7 说的那个问题：**一个不做事的步骤，看起来和做事的步骤一模一样。** 所以注入前加了 `assert touched > 0` —— 宁可崩，不要假装通过。

### 11.8 换真端点之后：前四轮的结论要修正（2026-11-23）

§11.4–§11.7 全部用 **subagent 充当 Judge**。这是个方法错误：

> subagent 是另一个模型、另一套系统提示、带着工具与自己的推理习惯。
> **我测的是 subagent 的性格，不是 Judge 的性格。**

拿到真端点（OpenAI 兼容，`AIPC-deepseek-v4.1-flash`）之后重做，结论变了。

#### 一、真实端点上，它根本不抖

同一份 10 条题库，`temperature=0` 跑 5 次、`temperature=1` 跑 5 次：

| | 不同结果数 | `ask_human` 次数 |
| --- | --- | --- |
| `temperature=0` | **1 种 / 5 次** | 0 / 10 |
| `temperature=1` | **1 种 / 5 次** | 1 / 10 |

**十次运行、两组设置，各自逐字节一致。** §11.5 说的「模式级分裂」在真端点上没有出现。

#### 二、但 `temperature=0` 和 `1` 结果不同

`0` 一次都不问人，`1` 问了 1 条。所以**固定 temperature 仍然必要** ——
理由从「防止抖动」改成「换了设置，结果就不同」。

#### 三、真正的问题不是抖，是自洽的错

真模型对那 10 条的判定（`temperature=0`）：

| 消息 | 判给 | 它给的理由 | 对错 |
| --- | --- | --- | --- |
| 汇报里把华东改成华南区 | work_001 | 修改汇报区域 | ✓ |
| 客户名单按行业分组 | work_002 | 客户名单分组 | ✓ |
| 预算表每个部门占一行 | work_003 | 预算表部门行 | ✓ |
| 另外把去年的数据也整理一下 | new_job | 去年数据另整理 | ✓ |
| 现在到哪了？ | chat_only | 询问当前进度 | ✓ |
| 标题改成季度经营回顾 | work_001 | 修改汇报标题 | ✓ |
| **再细一点** | **work_001** | **补充汇报细节** | ✗ 该问人 |
| **加一列同比** | work_001 | 汇报加同比列 | ~ 模糊 |
| **用红色** | **work_001** | **调整汇报颜色** | ✗ 该问人 |
| **明天要，急** | **work_001** | **明确交付时间** | ✗ 该问人 |

**注意右边那一列：它在编理由。**

「用红色」被解释成「调整汇报颜色」——用户从来没说过要改汇报的颜色。
「再细一点」被解释成「补充汇报细节」——补哪个细节？没说。

**这比不稳定危险得多。**

| | 用户能不能发现 |
| --- | --- |
| 抖动的错 | 能 —— 同样的输入两次不同结果 |
| **自洽的错** | **难 —— 它给了个像模像样的理由，看起来像听懂了** |

#### 四、`ask_human` 实际上几乎不触发

10 条里 0~1 条。而其中 3 条明显该问人。

**所以 `ask_human` 在真实使用中接近死代码。** 后果是：

> **「回显 ＋ 一键改」不是补充机制，是唯一的安全网。**
> 因为模型不会主动说「我不确定」，它会给每条消息都编一个归属。

#### 五、代价

一次 10 条的批量判定：**594 输入 + 2028 输出 token**，约 700~800 ms。

输出 token 是输入的 3.4 倍 —— 它是推理模型，每条消息都在「想」。批处理很划算，单条调用会很贵。

#### 修正汇总

| 原结论（§11.4–§11.7） | 真端点上 |
| --- | --- |
| 快照中性化有效 | **保留**：这条是结构问题，与模型无关 |
| 可复现性不成立 | **推翻**：10 次运行完全一致 |
| 必须 temperature=0 | **保留，换理由** |
| 程序化硬规则 | **仍然否决**：原因不变（静默错） |
| `ask_human` 率 10~62% | **推翻**：实际 0~10% |
| 「模式级分裂」 | **推翻**：那是 subagent 的行为 |

**方法论教训**：拿一个代理物去模拟目标系统，测出来的可能是代理物的性格。
subagent 便宜、好调，但它不是 Judge —— 该用真端点的时候，早点用。

### 11.22 L3 误判率与成本（2026-11-23）

`flowy-skeleton/l3_calib.py`。10 个简报 × 2 版本（对题 / 不对题）= 20 次调用。

| 版本 | 误判（对题→拦住） | 漏判（错题→通过） |
| --- | --- | --- |
| 原 prompt | **2 / 10（20%）** | 0 / 10 |

**20% → 0%，一个 prompt 条款。** 而且 10 个错题全部仍然拦住，**没有因为放宽而漏判。**

### 11.23 开发准入审查：四处被推翻（2026-11-23）

外部审查对照了真实 `flowy18_wip` 的 Rust 调用链，并在隔离环境重跑了反例。
**四处影响决策的发现，两处是我自己的 bug。**

#### 一、L3 的「0% 误判」是标签泄漏 → 真实是 30%

**原因**：`l3_calib.py` 把样本版本写进了页标题 —— `"C01 good"` / `"C01 bad"`。
而 `check_semantic.py` 会把页标题读进裁判正文。**等于把答案提前告诉了裁判。**

修掉之后重跑（中性标题「数据汇报」）：

| 版本 | 误判 | 漏判 |
| --- | --- | --- |
| 带标签（原数据） | 0 / 10 | 0 / 10 |
| **中性标题（真实）** | **3 / 10 = 30%** | 0 / 10 |

**被误杀的三个：C02（路线图）、C07（预算单位）、C10（培训计划）。**

**结论：L3 现在不能作为交付的裁决者。** 30% 的误判会让它在三天内被关掉。

#### 二、`bool()` 强转让字符串 `"false"` 变成通过

`check_semantic.py` 原来写的是：

```python
"ok": bool(out["ok"])
```

而 `bool("false") is True`。**模型只要把 `false` 写成字符串，就会被判成通过。**

已修为严格类型校验：

```python
if not isinstance(out["ok"], bool):
    raise TypeError(...)
```

#### 三、普通入口能带着核验失败走到交付（审查发现，我未独立复现）

审查在真实链路上得到的顺序：

```
verify(false, ANCHOR_MISSING) → branch → sign → deliver
```

另一次在同一路径更换附件后，**旧核验报告仍被门函数接受**。

**这说明 §11.16 的「日志里 0 条 `deliver`」只在骨架的专用路径上成立，普通入口没被测过。**

**要求**：宿主需要**唯一的交付入口**；验收必须从普通入口进入；独立观察发送端调用次数；核对发送的附件字节。

#### 四、「每个数都对」超出了核验能力（审查发现）

审查的做法：三页 PPT 里保留原来的「38 亿元」，**新增一个普通文本框**写同口径「99 亿元」。

重新打开后两句都在，**L1、L2 仍通过，L3 读到的正文也没有新增金额。**

**因为核验只认预先声明的那几个字段。** 声明之外的文本框，它根本不知道存在。

**所以对外的承诺必须收窄**：

> **系统只为「预先声明且重新核对成功的字段」背书。**
> 不是「文件里的每个数都对」。

并把「外部编辑后出现第二个报价」列入正式验收。

#### 五、路由规则自相矛盾（审查发现，我可核实）

方案同时写着：

| 位置 | 说的是 |
| --- | --- |
| §2.4 | **无来源不猜**，默认新建或问人 |
| §2.5 快筛③ | **当前只有一个活跃 work → 100% 直接归入** |

**只有 A 活跃时，新收的 B 正好命中冲突** —— 快筛③ 会把 B 错归到 A，而这正是 §2.4 禁止的。

**已按要求改**（§2.5）：

- 快筛只保留两条 —— `from_work` / `reply_to_card` / `ref` 有值；
- 「唯一活跃 work」**降级为弱提示**，只在问人时当默认选项，**不再自动归入**；
- 无来源的消息**先受理、独立落盘，再判归属**。

**「先受理」这条是关键**：不要因为归属没定就不接受输入。**B 必须能立刻拿到编号。**

### 11.23b 方法论教训：我测的全是「我想到的那条路」（2026-11-23）

这一轮被外部审查推翻的三条，**根子是同一个**：

工具批次的 future 不解出来，loop 就回不到读输入那一步。

**数字（7500 ms）对，解释错了。** 已改 §5.1。

### 11.18 核验的期望值从哪来，结论就反了（2026-11-23）

`flowy-skeleton/verify_gap.py`。

造一份「Worker 漏做一页」的产物，然后用两种期望来源核验：

| 期望来自 | ok | expected_fields | issues |
| --- | --- | --- | --- |
| **Worker 的缩水配方** | **True** | 8 | **0** |
| **完整需求** | **False** | 12 | **4（`ANCHOR_MISSING`）** |

**同一份产物、同一个核验算法，只换期望值来源，结论相反。**

#### 这说明什么

核验器拿 Worker 的配方当期望，就是**自己出题自己判卷**：Worker 少做一页，配方里也只有两页，照着一查全对。

**正确的分工**：

- 该有哪些信息点 → **需求方**（从简报抽）
- 这些点该落在哪 → Worker（配方）
- 落对了没有 → 核验器

**配方可以决定「放哪」，不能决定「有没有」。**

#### 顺带

这条也解释了为什么「三锚四码 8 条故障注入全过」并不能证明核验可靠 ——
那 8 条验的是**值和锚**，没有一条验**期望值来源**。

**故障注入只注入被检对象，不注入期望值。**

### 11.17 验收器崩了会不会放行（2026-11-23）

`flowy-skeleton/gate_failure.py`。五种验收器状态 × 两种失败策略，**以事件日志里有没有 `deliver` 为准**，不看函数返回值。

| --- | --- | --- |
| 正常放行 | 放行 | 放行 |

| 符合预期 | **2 / 5** | **5 / 5** |

**fail-open 把三种异常状态当成了通过。**

#### 这不是我们的假想

两家成熟实现都明写了这个坑：

- **Claude Code**：「On most events, when a hook fails or times out, Claude Code **still carries out the action**.
  A policy hook with a wrong path or a crashing script then **lets everything through**.」
  要阻断必须显式配 `"onFailure": "block"`。
- **ZCode**：「退出码 `2` 表达阻断；**其他失败、超时及非法输出会产生诊断，不能把所有异常都当作可靠拒绝**。」

**结论：验收层的失败语义必须是 fail-closed，且要写进验收清单 —— 光有「异常处理」不够，得专门测这一格。**

### 11.16 一秒不变式与核验硬门（2026-11-23）

#### 一、Router 自己干活会堵多久

`flowy-skeleton/router_block.py`。

场景：Router 里有一个耗时 **8 秒**的工具，你在第 0.5 / 1.5 / 2.5 秒各说一句话。

| 做法 | 第 1 句 | 第 2 句 | 第 3 句 | 最长 |
| --- | --- | --- | --- | --- |
| Router 自己调慢工具 | 7500.6 ms | 6501.0 ms | 5500.5 ms | **7500.6 ms** |
| Router 只派活立刻返回 | 0.1 ms | 0.1 ms | 0.1 ms | **0.1 ms** |

**差 72 469 倍。**

三个数字（7500 / 6500 / 5500）连起来看才是要害：**每句的等待 = 距离工具跑完还剩多久。**

这不是「慢一点」，是**每一句都在等那个工具**。

**结论**：Router 的工具必须是不阻塞的（微秒级），派活必须是投递而非 await。
两者合成一条：**Router 永远在一秒内回到可响应状态。**

#### 二、核验硬门是不是真的

`flowy-skeleton` 的 `run-gate`：造一份 3 个字段写错的产物，走交付。

| 步骤 | 结果 |
| --- | --- |
| 核验 | `ok=false`，`VALUE_MISMATCH` × 3 |
| 正常交付 | 被拒：`核验未通过：VALUE_MISMATCH` |
| **查日志** | **一条 `deliver` 事件都没有** |
| 强行越过 | 放行，记 `deliver_override` |
| 事件序列 | `verify → deliver_blocked → deliver_override → deliver` |

**验收方式必须是「查日志里有没有 deliver」，不是「看界面提示」。**

「被拒」很容易做成「提示拒绝、实际发出去了」。**只看提示文案的验证，等于没验证。**

### 11.15 运维四件套验收：10/10，以及一个假绿（2026-11-23）

`flowy-skeleton/opslab.py`，假事件源，不需要模型。

**每条都做「有机制 vs 没机制」对照** —— 只测「有机制时是对的」，全绿也说明不了什么。

| # | 测什么 | 没机制 | 有机制 |
| --- | --- | --- | --- |
| ① | 同一条事件投递三次 | **处理 3 次** | 处理 1 次 |
| ② | 一小时来 20 条 | 唤醒 **20 次** | 唤醒 12 次 + **攒住 8 条** |
| ③ | 失败那轮里有新事件 | 丢了 e3 | 4 条全收到 |
| ④ | 隔离区回收 | —— | 40 天已交付删、400 天未交付留、5 天不动 |
| ⑤ | 长跑增长 | —— | 100 轮 300 文件 3 MB，外推 1000 轮约 30 MB |

**10/10 通过。**

#### 但我第一次写的是假绿

第 ③ 项第一版这么写的：三轮里第二轮失败、返回空列表。

结果两种做法（失败推进水位 / 不推进）**输出完全一样**，都拿到 e1~e4 —— 因为失败那轮根本没带事件，
推进不推进都丢不了东西。**那个测试测的是空气。**

真实场景是：**失败的那一轮里，新事件已经存在，只是我们没拉到。**
改成带时间戳的事件源之后才见分晓：

```
正确（失败不推进）→ ['e1', 'e2', 'e3', 'e4']
错误（失败也推进）→ ['e1', 'e2', 'e4']   ← e3 永久丢了
```

**这和 §11.7 是同一类错误：一个不做事的验证，看起来和做事的验证一模一样。**
所以现在每条都强制有一个「没机制时会坏」的对照输出。

#### 结论

**运维四件套都是纯逻辑，成本极低，之前一条都没测过。**

现在补上了，而且证明它们是必要的 —— 少了任何一条，要么重复办、要么丢事件、要么把磁盘堆满。

### 11.14 第五种 kind：revise（纠正插队）（2026-11-23）

#### 问题

用户连着说两条，第二条是**纠正**：

```
"把华东区数据做成三页汇报，发给老王"   → 派活，attempt 1 开始跑
"不对，华东区改成华南区"               → ？
```

如果第二条只是「continue_job」排队：attempt 1 按旧方向跑完 → **出第一张卡（废的）** → 再跑第二轮 → **出第二张卡**。

**最贵的不是算力，是那张废卡。** 它污染了「交付物可信」这件事本身。

#### 机制：pi-rust 已经给了

`queue.rs` 的 **steering** 队列，注释原文：

> fired mid-run **after a turn's tool batch settles** (before the next LLM call),
> to inject guidance the app pushed while the model was working

**这就是插队。** `config.get_steering_messages = Some(hook)`，宿主决定注入什么。
把「被判为 revise 的消息」放进 steering 队列，pi-rust 在下一次 LLM 调用前注入 —— **一行不用改**。

#### 判据

**唯一标准：这条消息是否与已经说过的需求冲突？**

| 冲突？ | kind | 处理 |
| --- | --- | --- |
| 是（改区域、换数据、换主题） | **`revise`** | **插队**，注入当前 attempt，在途产物作废 |
| 否（加一页、改标题、调格式） | `continue_job` | 排队，下一轮 |

不是「会不会让在途产物变旧」——「再加一页附录」也会让产物变旧，但它没有推翻方向。

#### 实测：6/6（有状态）

| 消息 | 判定 | p | 理由 |
| --- | --- | --- | --- |
| 不对，华东区改成华南区 | **revise** | 0.95 | 区域从华东改华南，推翻方向 |
| 用二季度的数据重做 | **revise** | 0.90 | 改为二季度数据，推翻原数据口径 |
| 再加一页附录 | continue_job | 0.93 | 加附录页，属追加细化不冲突 |
| 标题改成季度经营回顾 | continue_job | 0.86 | 改标题属于细化，不推翻方向 |
| 算了，先停一下 | ask_human + **work_001** | 0.93 | 告诉你要停哪件（比只答 ask_human 更有用） |
| 客户名单也顺手整理一下 | continue_job + **work_002** | 0.86 | 已有对应 work，不必新建 |

**两条 revise 全对，判据清晰可用。**

#### 接进骨架之后：1 张卡 vs 2 张卡

`flowy-skeleton/` 的 `run-revise` 模式，两条路都跑了一遍（真模型判的）：

| 走法 | 渲染次数 | 出卡数量 |
| --- | --- | --- |
| **插队（判成 revise）** | 1 | **1 张** |
| 排队（强制走旧路） | 2 | **2 张** |

插队那条的日志：

```
"不对，华东区改成华南区" → revise work_001
理由：改区域，与已述需求冲突，推翻方向
→ 注入 steering 队列，下一次 LLM 调用前生效
→ 出卡 1 张（华南版）
```

**这就是用户提的那个浪费，现在有了数字。**

#### 所以四种 kind 变五种

| kind | 走哪条路 |
| --- | --- |
| `revise` | **插队**（steering 注入当前 attempt） |
| `continue_job` | 排队，下一轮 |
| `new_job` | 新建 work |
| `chat_only` | Router 自己答 |
| `ask_human` | 问人 |

### 11.13 多 work 交叉对话：有状态 8/8 跟对了（2026-11-23）

一个会话里交替说三件事，三句话各开一个 work。

#### 对话

| # | 消息 | 正解 |

| 2 | 客户名单也按行业分一下 | work_002 |

### 11.11 决策模型这个品类，以及提示词能追到哪（2026-11-23）

#### 先纠正一处

我们网关里的 `AIPC-auto-intelligence` / `-balance` / `-cost` **不是决策模型，是模型路由**——
先选一个模型，再由那个模型跑完整推理。

实测它们跑我们那套 Judge 提示词：**35 s / 37 s / 113 s**，token 消耗正常但墙钟极长。
这个耗时本身就说明它不是单次前向的判别，是「路由 + 完整生成」。

#### Jev 是什么

TypeSafe AI 2026-09-15 发布的 **System One** 决策模型。核心事实：

| 项 | 内容 |
| --- | --- |
| 定位 | 「让 AI 做出决策，而不只是生成文字」；LLM 擅长表达，JEV 专注判断 |
| 三种输出 | **`choice`**（多选）、**`score`**（打分）、**`noul`**（校准概率 0~1） |
| 架构 | 丢弃自回归循环，单次前向，毫秒级 |
| 关键卖点 | **Typed（固定类型）** ／ **Calibrated（校准概率）** ／ **Machine-first** |

官方示例里三个问题一次问完：`choice`「属于哪个主题」→ billing；`score`「紧急程度」→ high；
`noul`「是否需要人工」→ **0.93**，然后代码直接按 0.93 决策。

#### 我们用提示词追到哪：实测

同一批 10 条消息，让它输出 `p = 我这个归属判断正确的概率`（0.00~1.00）：

| 消息 | 判给 | p |
| --- | --- | --- |
| 汇报里把华东改成华南区 | work_001 | **0.98** |
| 客户名单按行业分组 | work_002 | **0.99** |
| 预算表每个部门占一行 | work_003 | **0.99** |
| 另外把去年的数据也整理一下 | work_001 | 0.35 |
| 现在到哪了？ | null | 0.30 |
| 标题改成季度经营回顾 | work_001 | 0.45 |
| 再细一点 | work_001 | 0.35 |
| 加一列同比 | work_001 | 0.40 |
| 用红色 | work_001 | 0.30 |
| 明天要，急 | work_001 | 0.30 |

**区分度是真的**：有直接对象词的三条 **0.98~0.99**，其余全在 **0.30~0.45**。
阈值 0.5 能挡住全部模糊消息，零放过。

#### 但它衡量的不是「正确概率」

看后三条：`现在到哪了？` 判成 null 是**对的**，`标题改成季度经营回顾` 判成 work_001 也是**对的**，
两者却都拿 0.30~0.45。

**这个 p 衡量的其实是「消息里有没有直接对象词」，不是「判断对不对」。**

而 Jev 的 0.93 是在验证集上校准过的，可以真的当概率用。**这是提示词追不上的部分。**

#### 对照表

| 维度 | 提示词 + 通用 LLM | Jev |
| --- | --- | --- |
| 固定类型输出 | **能**（JSON schema） | 原生 |
| 一次回答多个问题 | **能**（实测 10 条一批） | 原生 |
| 概率有区分度 | **能**（0.30 vs 0.99） | 原生 |
| **概率是校准的** | **不能** | 是 |
| 速度 | 600 ms ~ 4 s | **毫秒** |
| 批处理省钱 | 能（10 条 7740 token） | 更省 |

#### 结论：我们缺的不是决策模型

1. **形态能追平** —— 类型化输出、多问题一次问、批量，全用提示词做到了。
2. **速度追不上** —— 自回归 vs 单次前向，差两个数量级。
3. **校准追不上** —— 但**我们的场景不需要校准概率**。

**为什么不需要**：Jev 的 `noul: 0.93` 用来「直接执行不给人看」，所以必须可信。
我们的归属判断**出错会被回显**，用户点一下就能改——**容错设计替代了校准需求**。

**反过来推**：如果哪天 Flowy 要做「无人值守自动派活、不给任何人看」，那才必须上校准概率模型。
现在不是。

#### 但有一条要抄：把 `p` 用起来

即使 p 不是校准的，**它在「有没有对象词」这一维上很干净**（0.30 vs 0.99）。

比 `confidence: high|medium|low` 强 —— 三档标签是主观的，两位小数至少可排序、可设阈值。

**建议**：Judge 输出 `p` 而不是 `high/medium/low`，阈值取 **0.5**。

### 11.10 把问题改成是非题：测了，悬空（2026-11-23）

#### 做法

| 孤儿的是非题 | **2/5** |
| 总体 | 7/10 |
| token | 449 + 1594（对比纯多选的 594 + 2028） |

#### 关键是它为什么错

三条孤儿被答成 `no`（"不需要新工作"）：

- 「再细一点」→ `no`，理由「细化要求，非新工作」
- 「用红色」→ `no`，理由「样式调整，非新工作」
- 「明天要，急」→ `no`，理由「补充截止时间，非新工作」

**这三条答 `no` 在字面上是对的** —— 它们确实不是新工作。

**但「不是新工作」不告诉你归哪件。**

#### 这就是悬空

DSH 的 `no` 是有去处的：**订阅直达**。消息带来源、匹配订阅，不经 Eval 直接落到对应 Ticket。
所以它的 Eval 只需要回答是非题，`no` 意味着「别的地方已经接住了」。

**我们没有订阅机制，所以 `no` 无处可去 —— 那个 work_id 还是得有人给。**

**是非题只在「有结构兜底」时才成立。** 单纯把问题从多选改成是非，是把问题挪走，不是解决。

#### 唯一白捡的收益：来源

5 条带来源的消息，**零调用、全对**。

| | 纯多选 Judge | 加来源 + 是非题 |
| --- | --- | --- |
| 准确率 | 7/10（严格） | 7/10 |
| 模型调用覆盖 | 10 条 | **5 条** |
| token | 2622 | **2043** |

**准确率没变，成本和不确定性减半 —— 因为一半的消息根本不用问。**

#### 结论

**真正的杠杆不是「更好的 Judge」，是「消息从哪来」。**

| 做法 | 效果 |
| --- | --- |
| 消息永远带来源（哪个 work 页、回复哪张卡、点了哪个引用） | 大部分消息零成本直达 |
| 孤儿默认**新建或问人**，不猜归属 | 避免污染已有工作 |
| Judge 只处理剩下那一小撮 | 而且是**是非题**，不是多选 |

**先解决「消息从哪来」，再谈归属。** 这是我们架构里缺的那一环 —— 不是缺一个更聪明的判断器。

给输出加一个 `confidence: high | medium | low`，并把定义写死：

| 现在到哪了？ | chat_only | — | high |

**该 low 的 4 条全捞出来，没有误报。三次运行逐字节一致（`693+7047` token 也一致）。**

这直接修掉了 §11.8 说的「`ask_human` 接近死代码」。

#### 但有三个危险信号

**一、这个定义是我看着答案写的。**

p7/p9/p10 判错之后，我才写下「只要需要替用户补全主语，就是 low」——
**这和 §11.7 那张关键词表是同一个毛病**：在测试集上拟合规则。

要证它成立，必须用**另一套没见过的题**。现在不能算数。

**二、`ask_human` 从 0/10 涨到 4/10。**

之前担心「打断洪水」，现在成真了。而且 4 条里有「加一列同比」——用户可能真心觉得是给预算表加的，问一句反而烦。

**三、成本翻 3 倍。**

| | 输入 | 输出 | 合计 |
| --- | --- | --- | --- |
| 不加 confidence | 594 | 2028 | 2622 |
| 加 confidence | 693 | 7047 | **7740** |

**多付 3 倍 token，换一个字段。**

#### 老爷爷的意见（照录）

1. **confidence 只作排序信号，不作门。** 不要「low 就转人工」——low 只说明它自己没把握，
   **它完全可能高置信度地错**，那才是灾难。
2. **把问题从「属于哪件」改成「要不要开新事」。** 见下面 §11.9b。
3. **必须用另一套题复验**，否则测的是题库。

### 11.9b 成熟产品的做法：它们根本不猜归属

翻 DSH 自己的领域文档（`000-domain.md`），原文两句：

> **The main Session attaches a Thread to an existing Ticket only when its message points at that Ticket explicitly.**
> **a person's message that reaches a Ticket this way takes no Eval** (通过订阅直达的消息不过 Eval)

翻译成设计语言：

1. **有来源 → 直达**，不过任何判断。
2. **没来源 → 进 Eval**，而 Eval 决定的是 **「要不要开一件新工作」**，不是「归给哪件旧工作」。
3. **只有显式指向才挂到已有 Ticket。**

**它不问「这句话属于哪件事」，它问「要不要开一件新事」。**

| 产品 | 归属怎么定 |
| --- | --- |
| DSH Super-agent | 订阅直达；无订阅 → Eval 决定是否新建；显式指向才挂旧的 |
| LobeHub | 分界面：聊天就是聊天，建 Task 才算工作 |
| AutoLoop | 事项 = 规则 × 对象，规则固定，无归属问题 |
| GitHub / Linear / Slack | 人显式指定 issue / 线程 |

**行业共识：归属靠结构，不靠推理。**

#### 这暴露了我们方向上的一个偏差

| | 问题形式 | 候选 |
| --- | --- | --- |
| 我们原来的 Judge | 这条消息属于 001 / 002 / 003？ | **多选，歧义大** |
| DSH 的 Eval | 这条消息要不要开新工作？ | **是 / 否，歧义小** |

**多选比是非难判得多。** 而且多选题错一次就污染已有工作，是非题错一次只是多开一件。

#### 而且不对称的代价我们之前搞反了

我之前建议「已归属优先，宁可归错再改」——**这是反的**。

| 判错方向 | 后果 |
| --- | --- |
| 错归到已有 work | **污染它的记录、产物、签字** |
| 错开成新 work | 多一个空 work，合并或删掉即可 |

**所以默认应该倾向新建，不是倾向归旧。**

### 11.4 Judge 归属判定实测（2026-11-23）

**实验设置**：3 个活跃 work ＋ 6 条消息同时到达（当时的快筛全不中，全部落到 Judge）。

> 注：当时的规定是**三条**快筛。现在「唯一活跃 work」那条已降级为弱提示（§2.5），只剩两条。
> 这个实验的结论不受影响 —— 它测的是「有状态 vs 无状态」，不是快筛条数。
题库与打分器在 `judge-lab/`。

**两版快照，同一批消息、同一套规则：**

| 快照 | 准确率 | 一致性 |
| --- | --- | --- |
| 完整快照（含 `state` / `recent` / `artifacts`） | **4/6** | 3 次运行逐字节一致 |
| 中性快照（只有 `id` / `title` / `brief`） | **5/6** | 2 次运行逐字节一致 |

**失败模式不是随机，是系统性偏差。**

完整快照里 work_001 是「执行中 · 刚交了候选产物」，最显眼。**Judge 把几乎每条消息都归给它**——
包括本该属于 work_002 的「按行业分组，别按地区」。去掉状态字段后，这一条立刻判对。

#### 三条结论

1. **可复现性在高置信度题目上成立。** 这一轮 5 次运行完全一致——**但 §11.5 会证明模糊题上不成立**。「Judge 无状态」这个设计方向对，但光无状态不够。
2. **准确率首先是快照设计的问题，不是模型能力的问题。** 只改快照里放哪些字段，就从 4/6 变成 5/6。
3. **Judge 的快照必须中性化** —— 只给 `id` / `title` / `brief`，**不给 `state`、`recent`、`artifacts`**。状态越显眼，偏差越大。

#### 一处要诚实说明

剩下那处失误是「加一列同比」判给了汇报、而不是预算表。**这一条本身模糊**——汇报里也有表，加同比列同样合理。
严格算 5/6，宽松算 6/6。所以准确率的绝对数字不如「快照字段会稳定改变答案」这件事重要。

#### 对设计的直接要求

1. **「回显 ＋ 一键改」是必需品，不是锦上添花。** 5/6 意味着每六条就有一条会错。
2. **快照字段要有白名单**，不是把 work 的全部状态都喂给 Judge。

### 11.3 pi-rust 是不是全双工（实测，2026-11-23）

**结论：不是。它是「批间注入」的半双工。**

证据三条：

1. 循环里工具调用是同步的 —— `agent_loop.rs:343` 是 `execute_tool_calls(...).await?`，整批工具跑完才继续。
2. 库自带的测试就叫 `steering_injected_after_tool_batch_completes`，断言原文：
   > should inject queued messages **after all tool calls complete**
   > Both tools executed before steering was injected
3. `queue.rs` 的注释也写明：steering 在「一轮工具批次结束之后、下一次 LLM 调用之前」注入。

**但延迟上界不是整个 attempt，而是一个工具批次。** drain 发生在批次之后、下一次 LLM 调用之前，所以用户插话的等待 = 剩余工具批次时间。

**没有后台工具。** 代码里的 `BackgroundToolGuard` 是 FFI 生命周期管理，不是「工具异步化」。

#### 对我们的实际影响

实测我们两个工具（含 Python 启动）：

| 工具 | 耗时 |
| --- | --- |
| render.py | 451 / 466 / 688 ms |
| check.py | 372 / 465 ms |

**工具批次是亚秒级，所以首版够用。**

#### 什么时候会坏

长工具：大文件渲染、外部 API、二次模型调用、下载。那时用户要等整个批次。

#### 三个选择

| 选择 | 判断 |
| --- | --- |
| 不改，接受 | **首版采用** |
| **Flowy 层做两阶段工具** | **预留**：模型调 `start_render()` 立即返回，真正执行由调度层跑，完成后用 steering 投回结果 |
| 改 pi-rust 的 loop | 不建议 —— 会破坏它的 tool-call 语义，也跟不上上游 |

**一条要写进能力包约定的**：任何预计超过 5 秒的操作，必须写成 `start_x` / `check_x` 两阶段工具。这样长任务不阻塞对话，而 pi-rust 一行不用改。

代价要记住：两阶段会多一轮 LLM 调用，所以只用在长工具上。

### 11.2 Rust ↔ Python 进程边界（我们自己的实测，8 项全过）

零外部依赖，只用 `std::process`。项目在 `rust-py-boundary/`。

| 场景 | 结果 |
| --- | --- |
| S1 正常跑通 | 退出码 0 ＋ stdout 有结果 |
| S2 超时杀进程 | 设 2 s，实际 2.01 s；**kill 后 10.5 ms 确认退出** |
| S3a 脚本按约定失败 | exit 3 ＋ stderr 带约定标记 |
| S3b 解释器起不来 | exit 2 ＋ `can't open file`，与 S3a 可区分 |
| S4 大输出并发读 | stdout 5000 ＋ stderr 5000，**79 ms** |
| **S4b 串行读反证** | 先读完 stdout 再读 stderr → **读到 4444 行就卡死**，3.8 s 后才被看门狗杀掉 |
| S5 无运行时 | 不可解析的名字 / 不存在的绝对路径 → `NotFound` |
| S6 打断 | kill 后 10.6 ms 确认退出，随后 work 可放开 |

**四条能直接指导 V4 写代码的结论**

1. **必须并发读 stdout 和 stderr。** 串行读会在管道写满时死锁——这不是理论，实测卡在第 4444 行。
2. **std 没有超时 kill，要自己轮询 + 杀 + 再确认。** 杀完必须 `wait` 确认退出，才能放开 work（对应 §5.8）。
3. **`env("PATH","")` 不能模拟「运行时缺失」。** Windows 的可执行文件定位发生在**父进程上下文**里，子进程环境变量影响不到它。

   **所以不需要「运行时可用性检测」**——只需一个提前判据（`NotFound`），其余一律跑，失败后按 stderr 分类（§3.4）。**存根自己会把「怎么办」写在 stderr 里**，转述即可。

4. **退出码 → 四态映射**（已写进 `out/report.md`）：

| 观察到 | 判定 |
| --- | --- |
| exit 0 ＋ stdout 有结果 | `done` |
| exit 3 ＋ 约定标记 | `failed`（可重试） |
| exit 2 ＋ `can't open file` | `failed`（环境类，重试无用，报给人） |
| spawn `NotFound` | `missing` |
| 超时被杀 / 主动打断 | `cancelled` |
