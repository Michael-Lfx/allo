# 语音伴侣完整纵向执行 Plan

## 1. 执行目标与固定决策

依据[详细 PRD](/D:/workSpace/git_clone_test/allo/docs/architecture/voice-agent/PRD-voice-companion.zh.md)和[整合技术方案](/D:/workSpace/git_clone_test/allo/docs/architecture/voice-agent/voice-companion-integration.zh.md)，交付 Windows 上完整的“唤醒 → 对话 → 追问 → 真实任务 → 确认与取消 → 安装运行”流程。

已锁定：

- **Windows 完整交付，逐片串行验收。** Mac/Linux 保持结构兼容，分别实测后再宣称支持；不派发并行 Agent。
- **保留独立 `ai-mate`。** daemon 拥有声学和短对话；桌面宿主拥有窗口和产品状态；既有 runtime 拥有任务执行。
- **首期对话沿用现有 router。** 支持 Flowy Cloud 与已配置的 OpenAI-compatible 模型；设置页过滤不支持的协议，失效引用明确显示不可用。
- **快轨对话不初始化任务 runtime。** 任务连接失效不能阻断正常语音聊天。
- **固定体验参数：** 6 秒无语音退出、单句最多 30 秒、实际播放结束后 4 秒追问、最多三轮短上下文；确认听取最多 8 秒且不得超过执行侧授权有效期。
- **停止语音与取消任务分开。** 关闭窗口或关闭语音功能，不自动取消已接受的后台任务。
- 首版一个活动语音任务；每个任务使用专属 Conversation，不借用任意当前聊天或桌宠会话。
- 本期不增加流式 ASR、全双工 AEC、自定义唤醒词、远程客户端音频、新 runtime 或数据库迁移。

实施从当前 `feat/xiaozhi-voice` 的已有工作继续，保护未提交文档和其他改动，不重置领先的 40 个提交，不在 main 修改或提交。

## 2. 接口、状态与验证基础

### 产品状态与控制接口

保留现有 companion 路由和公开响应字段，统一跨进程 DTO：

- 状态接口增加声学、对话、播报和任务的实际可用性，区分用户启用意愿、启动过程和功能就绪。
- 配置接口保存对话模型引用、执行模型/预设和明确工作区；复用现有选择控件与 provider 解析，不保存第二份 API key。
- 事件流首帧返回完整产品快照，后续事件携带宿主 `instance_id/seq` 和对应快照。宿主是公开产品状态的单一写入者。
- 增加“停止指定语音会话”“取消指定任务”“确认指定工具调用”的控制入口。请求携带当前作用域，旧窗口或旧轮次请求返回冲突。
- 窗口先注册监听，再读取快照；按实例和序号处理竞态，不能靠固定延迟重发唤醒事件。
- daemon 私有控制接口限定回环地址，校验 supervisor 在启动时提供的临时控制凭据；凭据不进入命令行、日志或前端状态。

### runtime 对接

具体适配模块放在后端宿主，使用现有：

- `create_idempotent`：建立专属任务 Conversation。
- `send_message_with_idempotency_key`：提交真实目标。
- `public_turn_delivery_state`：只读核对接受与完成回执。
- 会话事件和运行状态：获得真实进展及结果。
- `cancel`、`list_confirmations`、`confirm`：控制当前绑定任务。

声学 `turn_id`、交付 `command_id` 和后台 `runtime_turn_id`分别保留，不能相互替代。创建和发送使用两个稳定幂等身份。

### 测试基础

使用现有回放管线接入生产 worker，测试替身只放在测试范围。统一记录：

- 输入交付、ASR 和模型调用次数；
- 会话、轮次、任务及回执身份；
- 实际状态序列、播放完成和取消结果；
- 每项 PRD 验收的自动测试、真机证据及签核状态。

测试应跨越生产入口，不能只验证枚举迁移或源码包含某个字符串。

### V7 的实现决定

执行侧只保留一个挂起与确认权威：

- 在实际派发入口增加仅语音任务启用的结构化策略检查，策略结果交给既有审批流程。
- 复用现有工具策略表的分类规则，不把其独立 token 和 suspended-call 存储再接成第二套生产审批系统。
- 限制取语音策略与既有 runtime 权限的交集；无法识别、越出工作区或不在支持范围内的调用直接拒绝。
- 通过实际工具调用测试证明文件删除、危险命令和路径越界受到约束，再开放高危任务。测试只验证“提示出现”不足以签核。

## 4. 每片验证与发布门禁

### 检查梯子

1. 运行该片的回放、接口、状态和失败路径测试。
2. 对受影响 crate 运行 `cargo test -p <crate>`、`cargo check -p <crate>`；依赖变化后检查生产 feature 图，确认没有 skeleton。
3. UI 变化运行行为测试、双语断言、类型检查、i18n、theme 及相关质量门禁；更新资源时运行 i18n 生成。
4. 切片集成后运行 `cargo fmt --all -- --check`、`cargo check --workspace`、`bun run check`、`bun run build:ui`和受影响桌面构建。
5. 真实桌面验证涉及录音、模型、物理扬声器、原生窗口或 runtime 的场景。替身测试和健康探针不得替代这些证据。

出现失败时记录基线失败与本片回归；不得通过降低断言、跳过真实路径或增加生产 fallback 让门禁变绿。

### 发布节点

- **R0：V0–V1。** 内部可验收的启用、唤醒、承载与退出路径，不对外宣称完整对话产品。
- **R1：V2–V4，并完成 V8 对聊天安装包的检查。** 可交付语音对话；任务能力仍明确不可用。
- **R2：V5–V7，并完成 V8 的全量回归。** 可交付真实任务和一次性口头确认。

窗口冷启动与热启动分别采样：目标 P95 分别不超过 1500ms、500ms。沿用既有四分类准确率、JSON 解析率和首音延迟门禁；采样报告同时记录模型、设备、网络、样本量和起止点。未达到指标时报告差距并修复，不把指标改成无数据的“体验正常”。

Windows 完成不等于 Mac/Linux 或无屏硬件签核，也不等于既有 72 小时挂机规程已经通过。
