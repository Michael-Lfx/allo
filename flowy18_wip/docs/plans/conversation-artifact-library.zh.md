## 1. 背景与核心痛点

### 1.1 用户任务与产品定位

用户在首页提出需求，Agent 在同一条对话中交付图片、文档、表格、幻灯片等文件。用户当场可预览和另存，之后可从资料库按名称、来源对话或类型找回，并回到文件交付的位置。

资料库承担对话成果的归集和查找。页面的文件来自明确的交付事件，生产入口不提供本地导入、拖入或目录扫描。文件在磁盘上保存是实现细节，不改变其对话来源。

**首版收录范围**：从全局首页新建入口开始的会话，以及这些会话的后续轮次中，Agent 经专用交付接口发布的文件。普通文字、Markdown 文件链接、工具中间文件、用户上传附件均不自动收录。项目专属入口、旧会话补录及其他来源留待后续阶段，不通过猜测工作目录判断来源。

### 1.2 当前实现的阻断点

1. 当前资料库通过本地选择器和路径引用工作，和已确认的产品来源不一致。
2. 运行中的聊天投影只有文本、推理、工具调用和工具结果，没有可靠的文件交付类型。
3. 工具的结构化结果经过 pi 适配后会丢失，不能靠解析助手文字重建文件来源。
4. 现有资料条目缺少稳定的交付 ID、来源会话与来源卡片锚点，无法准确跳回交付位置。
5. 已交付文件若继续引用可变工作目录，后续覆盖、删除或会话清理会改变已交付版本。
6. 资料库预览目前绑定资料库页面；对话也需要使用同一预览器和焦点返回规则。

### 1.3 能力对比

| 能力 | 当前工作区 | 本计划目标 |
| --- | --- | --- |
| 收录入口 | 添加本地文件、`FLOWY_LIBRARY_DATA` | 首页对话中的显式文件交付 |
| 对话呈现 | 工具文本与普通正文 | 文件卡片，状态来自宿主提交结果 |
| 文件保存 | 原路径引用 | 受控目录中的交付快照 |
| 来源 | 无稳定会话和卡片关联 | `session_id`、`submission_id`、`artifact_id` |
| 预览 | 资料库中的图片、PDF、PPTX | 对话和资料库复用同一预览器 |
| 其他格式 | 不支持内置预览 | 保留条目、另存和默认应用打开能力 |
| 收藏 | 界面内存 | 持久化，提供收藏筛选 |
| 原对话删除 | 尚无文件生命周期规则 | 文件仍可用，来源显示已删除 |
| 故障恢复 | 两处各自展示 | 磁盘提交可核对，聊天与资料库一致 |

### 2.2 首版范围

- 显式交付、受控快照、结构化凭证、持久恢复和防重复。
- 对话文件卡片；资料库列表、类型筛选、文件名与来源搜索、收藏。
- 共用图片、PDF、PPTX 预览；其他格式的可操作文件详情。
- 原生另存为、默认应用打开、回到原对话并定位文件卡片。
- 首页空态、搜索空态、加载、导出失败、来源删除、文件损坏等完整状态。
- 删除对话后保留文件；移入资料回收站可撤销，永久删除须明确确认并保留聊天中的删除状态。
- 清理生产本地导入和注入入口，保留隔离 example 与测试夹具。

### 2.3 后续阶段

- 在新对话中引用资料，显示可移除的引用卡片，发送前可检查。
- 自动读取资料内容、全文检索、语义检索和 OCR。
- DOCX/XLSX/CSV 原生内容预览、视频和音频播放。
- 内容缩略图、版本归组、批量导出和更完整的存储分析。
- 用户附件收录、项目专属会话、远端附件和云同步。
- 网页、可运行应用等交互成果：需要独立类型和打开契约，不能把文件分类当成支持声明。

### 2.4 架构不变量

1. 宿主核验并成功提交后才出现可操作的交付卡片与资料条目。
2. 不扫描助手 Markdown、不监听整个磁盘、不把所有 `write_file` 结果自动收录。
3. 一次交付在聊天、资料库、预览和导出中使用相同 `artifact_id` 与相同快照字节。
4. UI 和模型均不能指定管理目录中的绝对存储路径或自选 `artifact_id`。
5. 交付快照不会被后续生成覆盖；同名文件允许并存。
6. 文件交付和生成能力分开：可收录、可导出不代表有该格式的生成器或预览器。
7. 元数据变化、另存、预览和摘要计算均在后台处理，界面更新核对会话和请求代际。
8. 不把本方案描述为 OS 沙箱。现有 shell 权限边界保持原有事实，发布接口另做自身的文件校验。
9. 历史、文件或清单损坏时保留可诊断原件，避免用空记录覆盖故障数据。

## 3. 核心设计与模块规范

### 3.1 用户路径与界面

**A. 首页交付**

1. 用户从现有首页输入框发送请求，沿原来的 Agent 执行路径处理。
2. Agent 生成文件后调用 `publish_file`；宿主验证和暂存，界面仍显示当前生成状态。
3. 成功持久提交后，在该轮交付处出现卡片：类型图标、文件名、格式、大小；主交互打开预览，辅助操作为「另存为」。
4. 多文件按交付顺序呈现；相同 `artifact_id` 不重复展示。
5. 文件卡片不随成功工具详情折叠，不靠最终回复中的链接判断交付。
6. 用户正在向上阅读时，新卡片出现保留阅读位置，沿用现有新消息提示。

**B. 资料库查找**

- 去掉生产「添加文件」、本地拖入和生产 `FLOWY_LIBRARY_DATA` 通道。
- 顶部：标题、搜索、收藏筛选、排序、列表与网格切换。
- 默认用紧凑列表；每项呈现文件名、类型与大小、交付时间、来源对话标题。行内不显示存储路径。
- 搜索匹配文件名、显示名称、来源标题；类型筛选与收藏条件可组合。来源标题优先跟随现有会话标题，原会话删除后使用保存的标题快照。
- 首版采用现有类型系统中确有文件的分类，空分类可收起；「网站」「游戏」「移动应用」等名称不得暗示能直接运行。
- 排序基于真正的交付时间；名称排序有稳定 ID 作为次序兜底。
- 记录搜索、分类、视图、排序和滚动位置，离开再返回保留状态。

**C. 预览和文件操作**

- 图片/PDF/PPTX 复用当前受限预览管道，不另建聊天专用 renderer。
- 预览标题区域呈现文件名和来源；操作提供「回到原对话」「另存为」以及适用时的「用默认应用打开」。
- 详情来自受控快照。无内置预览的类型显示图标、元数据和操作，不把整个详情当成读取失败。
- 另存调用系统保存对话框，默认文件名为安全 basename；后台复制到用户选择的位置。取消不创建文件，已有目的文件按平台覆盖确认规则处理。
- 默认应用打开由宿主从主快照创建带安全扩展名的查看副本，再交给系统；外部应用的保存操作不能改写主快照。可执行文件、脚本等类型不提供直接执行操作，仍可另存。查看副本计入配额，正常退出或下次启动且无活跃操作时清理；无法判定外部应用是否仍在用时保留并提示，不能据时间猜测后强删。
- 复用 DESIGN.md 的 ModalLayer、dialog 和半径规则，预览关闭后焦点返回来自聊天或资料库的触发控件。

**D. 回到原对话**

- 菜单和预览均使用「回到原对话」；先校验来源，再进入现有 Studio 路由。
- 先选中来源 session，再等投影完成，按 `artifact_id` 找到交付卡片，映射为虚拟列表中的可见行并聚焦。
- 首版目标是准确定位交付卡片；UI 临时 row_id、数组下标和文本匹配不能充当持久锚点。
- 使用现有导航历史；Back 返回资料库原状态。来源定位失败时保留当前资料和可用操作。
- 全局空态「开始对话」调用真正的新建首页会话流程，不能仅跳到可能恢复旧聊天的 Studio 页面。

**E. 空态与错误反馈**

| 状态 | 呈现 | 可用操作 |
| --- | --- | --- |
| 真空库 | 在首页对话中生成的文件会自动出现在这里 | 开始对话 |
| 正在加载 | 正在加载资料 | 不显示误导的空库提示 |
| 搜索无匹配 | 未找到匹配资料 | 清除搜索和筛选 |
| 文件已交付但不支持内置预览 | 格式与大小，清晰说明 | 另存、适用时默认打开、回到来源 |
| 原对话已删除 | 来源对话已删除 | 预览、另存、收藏仍可用 |
| 文件缺失或校验异常 | 文件当前不可用，保留来源和元数据 | 重试核对、来源仍存在时回到对话 |
| 交付保存失败 | 本轮未能保存交付文件 | 重试交付；不显示成功文件卡 |
| 另存失败 | 目标位置不可写或保存失败 | 重新选择位置 |
| 资料库清单损坏 | 资料加载异常，文件已保留 | 后台重建派生索引、报告异常 |
| 达到存储上限 | 明确说明限制及已有资料仍可用 | 管理回收站、确认永久删除、取消本次交付 |

### 3.2 显式交付工具与运行上下文

新增宿主注册的 `publish_file` 工具。职责是交付一个已经存在的文件，不承担生成文件格式的职责。

建议输入：

~~~json
{
  "path": "report.csv",
  "delivery_key": "sales-report",
  "display_name": "销售汇总.csv"
}
~~~

- `path` 相对当前轮次输出根解析，必须落在当前会话、当前轮次分配的输出范围；不能从任意本地目录选择文件。
- `delivery_key` 为当前轮内稳定的交付槽位，1–128 字符；同槽位的相同内容重试返回同一回执，不创建新条目。
- `display_name` 可选，保留合法扩展名；过滤路径分隔符和控制字符，长度限制为 255 个 Unicode 标量。
- `session_id`、`submission_id`、源消息或工具调用 ID、时间和根目录均由宿主注入，不能信任模型参数。
- 符合首版范围的每次发送都必须由宿主生成并持久化稳定 `submission_id`；目前接受 `None` 的直接调用若缺少该 ID，不能发布文件。重试沿用原 ID，用户再次发送新建 ID。
- 已有 `ToolRunContext` 提供会话/Agent ID、`cwd` 和取消信号；需补稳定提交 ID、来源和当前交付输出根，不从 AgentEmitter 的文字推断。
- 保持同一 pi loop，使用当前 `ToolRegistry` 和 `ToolGuard`；不另建文件生成 Agent。
- `core` 通用工具返回增加专用可选交付元数据；只有当前宿主注册的发布工具且回执存在于暂存记录时才接受，忽略其他工具伪造的相同 JSON。
- 正常 `write_file`、`edit_file`、shell 结果只保留工具语义。用户明确要求交付时，由模型或生成器适配器显式调用发布接口。

**首页会话隔离**：当前非项目会话共享 `sessions/cwd`，不能据此判断归属。全局新建首页入口显式传入 `Home` 来源并使用专属工作目录，项目入口单独传 `Project`，不能凭当前 Studio 画面或继承的项目 workspace 猜测。当前轮次另有 `outputs/<submission_id>`。origin 和受控 workspace 元数据保存到 `core` 的 `SessionRecord`，UI index 只复制投影；UI index 损坏后从 `core` 重建仍能识别 `Home`。既有会话的 `cwd` 不静默迁移；旧会话来源为 `Unknown`，首版不自动回溯收录。路径初始化和 guard 变化先做专门审查，不改变 shell 运行权限。

### 3.3 文件存储与关键数据契约

在 flowy-agent 新增 `ArtifactStore`，先按模块实现，不新增共享 crate。flowy-app 持有的资料库 Catalog 逐步替换为 `AgentHandle` 的只读查询与操作接口；UI 不再单独维护一套文件真相。

建议磁盘布局：

~~~text
<app-data>/
  artifacts/
    staging/<session-id>/<submission-id>/<artifact-id>/
      payload
      prepared.json
    items/<artifact-id>/
      payload
      manifest.json
    deliveries/<delivery-id>.json  # 独立于会话的整轮提交标记
    views/<view-request-id>/       # 默认应用查看副本，含安全扩展名
    index.json                 # 可重建的检索投影
    preferences.json           # 收藏、回收站状态
  sessions/
    history.json               # 结构化交付凭证和原始历史
    index.json                 # 既有 UI 历史投影
    workspaces/<session-id>/
      outputs/<submission-id>/
~~~

`ArtifactStore` 的管理清单、整轮提交标记与快照独立于 sessions 生命周期。任何删除会话的代码不得级联删除 artifacts/items 或 deliveries。`index.json` 是缓存，重建以独立清单和已提交整轮标记为主，并核对历史中的未完成交付。

关键类型草案（字段命名允许实现时沿现有风格调整，语义不变）：

~~~rust
struct ArtifactReceipt {
    artifact_id: String,        // 宿主生成，不透明的 128-bit ID
    delivery_key: String,
    session_id: String,
    submission_id: String,      // 沿用已持久的 UI submission ID
    tool_call_id: String,
    display_name: String,
    media_type: Option<String>,
    size_bytes: u64,
    sha256: String,
    created_at_ms: u64,
}

struct ArtifactManifest {
    schema_version: u32,
    receipt: ArtifactReceipt,
    origin: SessionOrigin,     // Home / Project / Unknown
    origin_title_snapshot: String,
    payload_relative_path: String,
    publication_state: PublicationState,
}

struct ArtifactPreference {
    artifact_id: String,
    favorite: bool,
    trashed_at_ms: Option<u64>,
}

struct DeliveryCommit {
    session_id: String,
    submission_id: String,
    artifact_ids: Vec<String>,
    completed_successfully: bool,
}

enum ChatLine {
    // 保留全部现有变体。
    Artifact { artifact_id: String },
}
~~~

- 来源锚点以 `artifact_id` 为准，回执中的 session/turn/call 用于定位和去重。现有 message ID 生成方式无需为本功能做全仓重写。
- 原始 basename 和显示名分开；首版暂不提供「重命名」，后续如提供，明确只修改显示名。
- 快照 `hash` 用于完整性与重复核对，不把跨会话相同内容合并成一个资料条目。
- 对话和列表的显示 DTO 从宿主记录生成，不在 `ChatLine` 中再复制一份可变路径。
- 所有新增可选历史字段具备 `serde` 默认值，旧版本记录可读。管理清单带版本号，未知未来版本拒绝覆盖。
- `DeliveryCommit` 与该轮历史原子写入同一 `core` `SessionRecord`，必须携带完整的交付 ID 集合；它不是普通 tool result，也不能用会话的最新状态替代。独立 deliveries 标记完成后保留同一集合与来源快照，原对话删除不影响它。
- 具体 `hash` 依赖实施时核对已有锁定包，直接使用时在 workspace 显式声明，避免依赖传递可见性。

### 3.4 快照校验与预算

1. 发布从受控输出根打开普通文件；拒绝目录、空文件、路径越界、符号链接或重解析点绕过及取消后发布。
2. 通过同一打开句柄分块复制和计算 `hash`，读取有界，记录实际复制字节。复制期间源被修改时拒绝或重试核对，不形成半文件交付。
3. 临时 `payload` 写完、同步，再原子提交清单；最终存储位置由 `artifact_id` 决定。
4. 扩展名和已知内容头不匹配时返回可理解的交付错误。可预览格式按现有有界读取策略检查，其他类型不为分类而全量解析。
5. 「已交付」证明真实快照存在并通过基础核验；不等于已证明 PPTX 页数、CSV 数据或业务内容满足所有用户要求。专业生成器的内容验收另列。

首版预算草案：

| 资源 | 限制 | 行为 |
| --- | --- | --- |
| 单文件快照 | 128 MiB | 超限拒绝本次交付，不截断 |
| 一轮交付 | 8 个文件，合计 256 MiB | 生成说明中提示，按整轮提交规则处理 |
| 已提交、暂存与查看副本总量 | 5 GiB | 写前预留预算；超限不继续拷贝 |
| 独立清单 | 每份 64 KiB | 有界读取，超限隔离 |
| 保有 `payload` 的文件记录 | 首版最多 1,000 个，含回收站和预留记录 | 同一宿主序列检查数量与字节预留；永久删除后释放占额 |
| 资料库聚合索引 | 4 MiB | 可从清单重建；不可凭空创建交付 |
| 清单、回执与删除墓碑元数据 | 合计 16 MiB，受控扫描最多 10,000 个条目 | 到达上限拒绝新增并报告；不把部分扫描结果提交为完整索引 |
| 预览 | 沿用当前 128 MiB 输入、1,600 万像素与 ZIP 预算 | 不把快照存储预算等同于渲染器整体内存上限 |

这些预算约束 `ArtifactStore` 的快照、暂存、查看副本和元数据；生成工作目录及 shell 自身的磁盘使用不因此自动受限。该限制必须在实现和验收记录中如实区分。永久删除快照保留紧凑墓碑以阻止旧历史重放；墓碑占用独立元数据预算，不计为仍保有 `payload` 的 1,000 个文件。

### 3.5 提交时序、崩溃恢复和并发

~~~mermaid
sequenceDiagram
    autonumber
    participant U as 用户
    participant P as pi 工具执行
    participant A as ArtifactStore
    participant H as Engine 历史
    participant V as 聊天与资料库
    U->>P: 首页请求生成文件
    P->>A: publish_file 和宿主运行上下文
    A->>A: 校验、复制快照、保存 prepared
    A-->>P: 暂存凭证，尚未对外宣布交付
    P->>H: 轮次完成与可信凭证
    H->>H: 原子保存历史及成功 DeliveryCommit
    H->>A: 确认已持久的完整交付集合
    A->>A: 补齐所有快照后提交独立整轮标记
    A-->>V: CommittedArtifact 事件
    V->>V: 同一 ID 更新卡片与资料库
~~~

多个磁盘位置不能宣称拥有单一原子事务。本方案采用「暂存快照 → 历史与成功 `DeliveryCommit` 同步落盘 → 独立清单全部完成 → 整轮标记 `committed` → 通知」，以 `prepared` 状态和幂等恢复补齐中断窗口。首次发布的整组文件必须同时可见；在第 1/N 份清单提交后崩溃时，恢复先补齐其余文件，再一次发布整组。已发布后个别 `payload` 丢失则逐项显示不可用，不把其他文件隐藏。

| 中断点 | 重启后的处理 |
| --- | --- |
| 复制未完成 | 不产生卡片；清理不可交付的临时片段 |
| `prepared` 存在，历史无凭证 | 不自动交付；隔离为待核对，记录诊断 |
| 历史只有 tool result 凭证，该轮失败或取消 | 不交付；会话之后又成功也不能改变旧轮结论 |
| 历史有成功 `DeliveryCommit`，独立清单仍 `prepared` | 核对完整 ID 集合、`hash` 和预算，补齐整组并提交独立标记；保持原 ID |
| 部分独立清单完成，整轮标记未提交 | 不对 UI 暴露部分集合，恢复整组后再发布 |
| 独立整轮标记 `committed`，聚合索引未更新 | 从标记与清单重建索引，不重复复制文件 |
| 历史或清单读取失败 | 暂停自动清理并显示恢复异常，保留文件 |
| 会话有确认删除记录，独立整轮标记 `committed` | 文件继续可用，来源显示已删除 |
| 部分文件无法恢复 | 每条显示自身状态，不用一个错误清空整个库 |

首次恢复仅扫描受控 artifacts 清单，后台有界、可取消。未提交但完整的 `prepared` 文件保留 7 天用于核对；只有确认历史可读且没有成功 `DeliveryCommit` 后才按保留期清理。正常 `committed` `payload` 不自动按时间删除。删除来源会话与交付提交/恢复在同一宿主序列中协调：先确认该会话已持久交付的独立整轮标记全部提交，再允许删除历史，避免先删掉唯一的恢复证明。

**提交失败约束**：当前 `Engine` 在历史保存失败后仍可能调用 `finished`，且失败记录会留在内存。交付逻辑必须单独要求成功落盘的 `DeliveryCommit`；失败时回滚未提交的 artifact 引用和该轮交付标记，不能让下一次普通历史保存把失败交付「复活」。会话恢复代码也必须遵守同一提交状态。`prepared` 工具凭证可以作为失败诊断保留，但始终没有可操作卡片资格。

**并发**：复用 `RunFence` 及取消代际，所有发布记录绑定 session、submission 和 artifact ID。元数据由一个宿主写入序列提交；后台文件复制可以排队，首版单个复制任务，防止多个文件同时膨胀内存与磁盘占用。清理不得触碰仍在运行或恢复中的 staging。

**整轮规则**：首版仅在该轮成功完成且历史写入成功后提交文件集合。轮次失败或取消时，本轮 `prepared` 不进入资料库；已在先前轮次交付的文件不受影响。该规则写入工具说明，工具返回「已暂存」而非「用户已收到」。

核心成功 `DeliveryCommit` 的持久化是交付的线性化点。在此之前取消使本轮交付失效；在此之后收到取消只停止尚未开始的工作，已提交交付由宿主完成独立标记和通知，不再回滚文件。UI 在这段收尾期间显示「正在保存文件」，不先显示「已取消」再突然出现文件。

**状态机与合法迁移**：文件可用性（正常、缺失、校验异常）和来源可用性（正常、已确认删除、暂不可用）单独计算，不伪装成发布状态。

| 状态 | 合法下一状态 | 前置条件与界面资格 |
| --- | --- | --- |
| `Copying`（仅运行中） | `Prepared`、`Rejected` | 有效运行代际与额度预留；无可操作卡片 |
| `Prepared` | `Committed`、`Rejected` | 仅成功 `DeliveryCommit` 加整轮独立标记可进入 `Committed`；未提交无列表资格 |
| `Committed` | `DeletePending` | 可预览和收录；回收站用独立 `trashed_at_ms`，可移入、恢复而不改变发布状态 |
| `Rejected` | 同一交付 ID 的终态，重试使用新的有效提交 | 不对外宣称交付；可复用核验过的字节但不能复活旧回执；诊断文件有界保留 |
| `DeletePending` | `Deleted`、保持 `DeletePending` | 等待读句柄和删除结果；禁止新文件操作，不提前释放额度 |
| `Deleted` | 终态 | 保留墓碑，旧回调和历史恢复不能重新发布 |

整轮发布标记从 `Prepared` 进入 `Committed` 后不被轮次后续状态覆盖；组内单项永久删除保存为墓碑，其他已交付文件仍可用。

### 3.6 幂等、同名和版本

| 情况 | 结果 |
| --- | --- |
| 同回调或同 submission 重放 | 相同回执，不增加条目 |
| 同轮同 `delivery_key`、相同字节 | 返回已有 `artifact_id` |
| 同轮同 `delivery_key`、不同字节 | 返回冲突；模型须使用新的交付槽位或重新请求修订 |
| 不同轮同名文件 | 新 `artifact_id`，旧快照保持不变 |
| 不同会话同名或同 `hash` | 各自保留来源，不跨会话去重 |
| 用户再次明确生成 | 新 submission 和新交付；不误当作旧事件重试 |
| 已移入回收站或永久删除的资料收到旧事件 | 保持回收站或删除状态，不被重新加回 |

首版不做复杂版本树。列表用交付时间和来源区分同名文件；未来通过可选 supersedes 字段建立修订关系，不能覆盖旧字节来模拟版本。

### 3.7 删除、收藏与来源保留

- 删除原对话：独立 manifest/payload 和整轮标记保留，收藏及资料状态保留；来源变为不可跳转，保留标题快照。
- 从资料库移除：进入资料回收站，不删除文件或聊天卡片。显示撤销；「资料回收站」提供重启后仍可使用的恢复入口，同轮事件重放不移出回收站。
- 回收站恢复：同一 ID、收藏和来源恢复到默认列表，不新增快照。
- 永久删除：只在回收站内提供，先说明会让原对话中的文件卡片也无法预览和另存，明确确认后删除受控 `payload`，保留紧凑的已删除墓碑；不删除用户另存的副本或生成工作区文件。
- 聊天中的永久删除卡片保留文件名和「文件已删除」状态，不重新从可变源路径找回，不显示可用的文件操作。
- 收藏：存入独立 preferences，重启保留。收藏筛选只作用于未进入回收站的资料。
- 恢复与索引重建保留回收站、收藏和永久删除墓碑，不从历史扫描覆盖用户选择。
- 资料库显示已用空间和上限。回收站仍占配额；只有确认物理 `payload` 已删除才释放对应文件数和字节额度。不自动删除最早文件。

**永久删除的提交顺序**：暂停该 ID 的新预览/导出，等待宿主正在读取的操作释放句柄，原子写入 `DeletePending`，再删除受控快照并提交 `Deleted` 墓碑。任一步失败显示待清理，不提前释放额度；重启后根据 `DeletePending` 幂等补清理。受外部应用占用的查看副本单独显示待清理字节，不强删正在使用的文件。不按 7 天或配额压力自动清空回收站。

**来源删除入口的依赖**：`core` 已有 `Engine::remove_session`，但 `AgentHandle` 和侧栏尚未暴露完整用户操作。M2 增加宿主删除服务，协调取消、已提交交付组、`core` 历史、UI index 和删除墓碑；M5 增加会话菜单「删除对话」及确认，说明资料库文件仍保留。保存失败不提前移除会话。未接 UI 时仅能声明服务层生命周期测试通过，不能把夹具删除当作用户验收。

**来源状态的表达**：只有宿主已确认会话被删除时，才显示「来源对话已删除」。历史文件读取失败、权限异常、会话暂未加载和确实找不到来源分别按可恢复的「来源暂不可用」处理，不把存储故障伪装成用户删除，也不因此改变已交付快照和资料库显示状态。

### 3.8 聊天历史与来源定位的实现注意

- `core` 的 `ContentBlock::ToolResult` 增加默认兼容的专用交付凭证字段，模型上下文转换可省略该字段，仅保留正常工具内容。
- RegistryTool 已有 `Success.value` 到 pi details 的传递；`EngineEmitter` 和 `to_host_messages` 当前会丢失，应补完整并验证可信来源。
- `lines_from_messages` 当前按 Role 分支处理工具结果，但实际工具结果以 `Role::User` 存储。先按内容块提取工具结果和交付凭证，避免把它当普通用户文字，其他内容维持原顺序。
- `ChatLine::Artifact` 仅从已提交整轮集合和宿主记录派生，历史重建去重；回收站不影响聊天可用性，永久删除显示墓碑状态。内存 UI index 不作为唯一事实来源。
- history.rs 判定轮次完成时跳过 Artifact 与 TaskReceipt，并保持卡片在工具折叠之外。
- `ChatFeed` 将 `artifact_id` 映射到当前源行，再经 `Projection::source_rows` 找到可见行；会话未加载时保留 `pending` reveal 请求，加载后只消费当前请求。
- 允许标题更新，不把标题字符串当来源身份；来源会话删除后不创建一个虚构会话。

## 4. 关键决策与权衡矩阵

| 编号 | 决策 | 选定方案 | 其他方案及取舍 |
| --- | --- | --- | --- |
| D1 | 收录来源 | 首页对话中的显式交付 | Markdown 抽取缺乏真实性；磁盘扫描会混入中间文件 |
| D2 | 交付入口 | 宿主 `publish_file` + 可信凭证 | 所有写文件自动收录无法分辨工程文件与给用户的成果 |
| D3 | 文件所有权 | 独立快照和清单 | 原路径引用无法保证删除对话或后续覆盖后的可用性 |
| D4 | 单一记录 | `ArtifactStore`，通过 `AgentHandle` 暴露 | 聊天与资料库分别保存路径会产生分叉 |
| D5 | 来源锚点 | `artifact_id` + 稳定会话/轮次信息 | UI 行号、正文匹配、临时 row_id 会变化 |
| D6 | 提交时机 | 轮次成功及历史、清单双重提交后发布 | 普通 tool_end/finished 不代表文件已持久 |
| D7 | 中断恢复 | 成功 `DeliveryCommit` 与独立整轮标记 | 仅凭工具成功或会话最新状态无法判断某一轮的交付资格 |
| D8 | 格式能力 | 交付、生成、预览分别声明 | 不能因为已有 PPTX 预览就承诺能真实生成 PPTX |
| D9 | 新工作区 | 首页新会话隔离、旧会话保持 | 沿用共享 `cwd` 不能保证产物归属；全量迁移会扩大风险 |
| D10 | 删除对话 | 文件独立保留 | 已由用户明确确认，不级联删除成果 |
| D11 | 手动移除 | 回收站、持久恢复、确认永久删除 | 只隐藏无法回收配额；直接删文件缺少撤销与影响说明 |
| D12 | 技术边界 | 当前 GPUI Rust 工作区，无新共享 crate | 本方案不套用父仓库 Tauri/React/backend 的路由与 DTO |

## 5. 验收标准与验证矩阵

### 5.1 用户可观察的出口标准

首版完成必须同时满足：

1. 全局首页发真实请求生成 CSV 或 Markdown，交付后对话卡片和资料库只有一个相同 ID，实际文件内容正确。
2. 一份真实多页 PPTX 和 PDF 经同一发布链路成功收录和预览；这条链路测试使用夹具，不能冒充已接入实际 Office 生成器。
3. 重启后文件、来源、收藏和回收站状态均可恢复；删除对话后文件仍可预览和另存。
4. 从长历史中的资料跳到准确交付卡片，返回资料库仍保留搜索和滚动位置。
5. 任何未真实生成、未核验或未持久提交的文件都不会显示为成功交付。
6. 生产页面与代码路径没有本地导入按钮、文件夹扫描、生产注入数据和演示回退。
7. 用户能从回收站恢复资料，也能在确认影响后永久删除以实际释放空间；重启或旧事件不能让已删除文件复活。

### 5.2 独立验收用例

| 编号 | 操作与输入 | 可断言结果 |
| --- | --- | --- |
| TC-01 | 首页生成真实 CSV 并发布 | 内容可核对，同一 ID 出现在聊天与资料库 |
| TC-02 | 发布真实多页 PDF、PPTX 夹具 | 两处预览同字节、同页数；标明是交付与预览测试 |
| TC-03 | 普通回答、Markdown 假路径、普通 `write_file` 中间文件 | 零资料条目、无可点击假文件卡 |
| TC-04 | 发布失败或不存在的文件 | 明确错误，零成功交付 |
| TC-05 | 重放同 submission/同回调/同槽位相同内容 | 只有一个条目和同一份快照 |
| TC-06 | 同槽位不同内容 | 冲突被拒绝，旧版本字节不变 |
| TC-07 | 不同轮或会话生成同名文件 | 各自 ID、来源和旧字节保持不变 |
| TC-08 | 交付后修改或删除工作区源文件 | 已交付快照 `hash` 不变，仍可预览 |
| TC-09 | 对话和资料库重启恢复 | 卡片、来源、收藏、回收站一致 |
| TC-10 | 历史写入失败，随后另一轮保存成功 | 失败交付不被复活，不误报成功 |
| TC-11 | 各提交窗口强制中断 | 按 §3.5 恢复，已确认交付不丢失，不重复 |
| TC-12 | 取消、切会话、迟到 `tool_end` | 旧轮次不能发布到新会话或资料库 |
| TC-13 | 两会话并发同名交付 | 工作区、暂存、快照和回执彼此隔离 |
| TC-14 | 越界、符号链接/重解析点、复制中变动 | 发布失败，无越界快照和半文件 |

| TC-19 | 移入回收站、撤销、重启后从回收站恢复 | 状态持久，恢复沿用同一 ID，不删除聊天卡片或文件 |

| TC-25 | 启动时清单损坏或版本未知 | 保留原件，不覆盖为空，不误清理 `payload` |

### 5.3 验证梯子

每个阶段只跑覆盖变动的最小测试；Cargo 构建和测试串行执行。代码冻结后运行一次完整矩阵。

~~~powershell
# 相关阶段的最小检查。
cargo test --offline --locked -p flowy-agent-core --lib -- --test-threads=1
cargo test --offline --locked -p flowy-agent --lib -- --test-threads=1
cargo test --offline --locked -p flowy-studio -p flowy-app -p flowy-i18n --lib -- --test-threads=1

# 代码冻结后的整体验证。
cargo check --workspace --offline --locked
bun scripts/check-ui-contracts.mjs
cargo build --offline --locked -p flowy-desktop
~~~

Windows 先按 [构建踩坑记录](windows-build-rebase-pitfalls.md) 导入 MSVC 环境，TEMP/TMP 指向工作区可写目录。格式检查限本次变动文件。Clippy 运行并记录本次问题与已有阻挡，不为过关顺带修改无关文件。

原生人工验收：隔离应用数据目录；真实首页 CSV 生成、受控 PPTX/PDF 发布、两个会话切换、重启、来源跳转、删除对话后文件仍可用。截图至少覆盖中英核心状态、亮暗、800×600；UIA 能力与截图分别记录，不互相替代。

性能验收：固定同机窗口/DPI，以 0、100、1,000 条资料和千行历史测首个可交互帧、筛选、来源跳转。M0 先采当前基线，目标是不在 UI 线程做文件 I/O，筛选和跳转不出现可感知冻结；若新增行为比基线慢超过 20% 或界面长任务超过 100 ms，先定位再扩功能。数值为待实测门槛，不当作已有性能结果。

## 7. 兼容处理、风险和交付门禁

### 7.1 当前本地导入实现的处理

- 生产入口移除 `AddFilesRequested`、系统多选导入、`FLOWY_LIBRARY_DATA` 读取和目录 Catalog 写入路径，保留预览器、文件图标、筛选和通用交互。
- 已存在的 `library.json` 原样保留并停止写入，不把这些路径伪装成对话成果；不静默删除或迁移用户文件。
- examples/library.rs 和自有 fixtures 可保留显式本地输入用于 renderer 验证，不能由生产加载错误触发。
- 测试随正确产品契约更新；旧路径的正常测试保存在 Git 历史，文档清楚记录被取代原因。

### 7.2 专业格式生成能力

当前内置工具包含读写、编辑、搜索及平台 shell，没有独立的 PPTX、PDF 或图片生成器。已有 PPTX/PDF renderer 只证明预览可用。

M0 必须分别列出：

| 目标 | 首版证据 | 扩展条件 |
| --- | --- | --- |
| CSV/Markdown 生成 | 真实首页请求 + 现有 `write_file` + `publish_file` | 内容和回执核验通过即可用于纵向切片 |
| PDF/PPTX 文件交付 | 自有真实 fixture 通过同一发布工具 | 这是链路测试，不宣称真实生成 |
| PDF/PPTX 专业生成 | 先探测已有可用且许可合规的生成能力 | 确认输入、输出、页数/业务内容与可编辑性后单独接入 |
| 图片生成 | 首版可交付现有生成器的真实文件 | 外部能力未接入前不提供无效生成承诺 |

### 7.3 发行阻挡

前一轮核查发现回退字体许可不完整，且 Dioxus/macOS 打包流程未收录完整声明。将其列为 M6 的发行门禁，包含 PPTX fallback 及 Hayro/Foxit 的相关声明、资源清单和安装包解包核对。

本计划只记录门禁。触及发行配置、签名和 bundled assets 时，先按仓库 AGENTS 的高风险区要求取得授权，再做具体修改；本轮制定方案不改变打包文件。

### 7.4 风险与应对

| 风险 | 应对和停止条件 |
| --- | --- |
| 错把内部文件当交付 | 只接受专用可信发布工具；假链接与普通写文件必须有负向测试 |
| 历史保存失败但界面报成功 | 独立 `committed` 回执屏障；保存失败与后续轮次联动回归 |
| 删除会话同时删除文件 | 物理路径与生命周期分离；TC-18 必过 |
| 工作区归属混乱 | 新首页会话隔离；`Unknown` 旧来源不猜测补录 |
| 重启后两处展示分叉 | Manifest 为独立文件事实，历史为来源引用；重建和去重规则单一 |
| 格式支持承诺过大 | 生成、交付、预览分列；专业格式能力有独立实测门槛 |
| 存储持续增长 | 有界预算、可观测配额、回收站与确认永久删除；配额无法回收时禁止公开交付 |
| UI 弹层冲突与来源错位 | 宿主统一预览、待定位请求代际、虚拟列表卡片锚点 |
| 既有历史不兼容 | `serde` 默认值、旧文件夹具、`Unknown` 来源和不覆写故障数据 |
| scope 扩张到所有附件/项目/云 | 首版严格按确认来源实施，其他类型单独排期 |
