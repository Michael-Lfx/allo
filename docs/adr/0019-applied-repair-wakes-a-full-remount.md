# ADR-0019: 修补应用后唤醒一次全量重挂——ADR-0018 决定 4 自动路径边界的有条件例外

Status: Accepted

Date: 2026-11-26

## Context

ADR-0018 决定 4 给生长唤醒划了自动路径边界：挂载失效（结构变过，或从未挂载）、
待挂节点超过 8 时不由唤醒触发，退回手动「结构对齐」。理由是生长是纯加法，不该在
一次生长之后突然附带一次大调用。

结构修补（ADR-0012 / j09）会改结构。结构 hash 一变，全部挂载失效；修补回合自己
不碰挂载表。2026-11-25 的取证（`docs/tracker/learning-maintenance-loop/map.md`）：

- 修补回合此前从未运行：定时臂的到期判定被每个 tick 的无条件重置废掉，手动入口
  零点击。所以「修补后挂载全失效」从未在生产里发生过，也就没有人为它修过路。
- 定时臂修好之后，一次 `applied` 修补会让该课的挂载静默全失效——地形清单退回
  全量（ADR-0018 决定 2 的收益归零）——而当时没有任何自动链路把它挂回去：生长
  唤醒对 stale 一律拒绝（`service/growth_wake.rs` 的 `growth_wake_verdict`，第一
  道判定）。
- 真机采样（2026-11-25/26，同一门课 12 个独立样本）：修补 3 次 `applied` / 9 次
  `noop`。`applied` 都是纯加法（补结构块、补 assumes / contrasts 边），其中两次是
  对「前置底座缺口」留痕的结构回应。修补确实会改结构，只是不频繁。

## Decision

_修订 ADR-0018 决定 4 的自动路径边界——值得重开，因为那条边界的理由（生长唤醒
不该突然附带一次大调用）针对的是「生长」这种与挂载失效无关的触发源；而修补正是
让挂载失效的那件事本身，由它触发的重挂是必要善后，不是意外的大调用。_

修补 `applied` 之后登记一次**修补后重挂**意图（`RepairFollowupWake`），复用 sb2
唤醒通道的设施——同一个 `Notify`、调度器的同一个唤醒分支——但它是一种独立的
意图，有自己的登记表和准入：

- **登记不设准入**：`run_structure_repair_with_trigger` 在 `applied` 的 Done 账本
  行之后、水位推进之前登记。结构已经变了就必须重挂，不因水位记账失败而丢。
  `noop`、`skipped`、失败、取消都不登记。
- **执行时复核**，不启动的原因各留一行 info 日志：自动维护运行期关；课程不在维护
  面；**从未挂载**（无挂载行）；挂载未失效且无待挂节点（登记到执行之间已经有人
  挂过）。
- **不设待挂阈值、不去抖**：全量重挂正是这条意图的目的，而它只会紧跟一次刚改过
  结构的修补。
- 账本触发源 `repair_followup`（界面显示「修补后重挂」），不与「随生长附带」混淆。
- 定时臂路径同样登记：tick 在同一回合里内联挂载之后，这条意图复核为「无事可
  重挂」，零 LLM 零账本。

这是对 ADR-0018 决定 4「挂载失效不由唤醒触发」的**有条件例外**：失效原因是本系统
自己的修补时，由系统自己挂回去；其余失效（从未挂载）仍走手动。生长唤醒的三道闸
与其测试原样保留。

## Consequences

- 修补之后地形清单不会静默退回全量。真机读数见 m2 Resolution
  （`docs/tracker/learning-maintenance-loop/tickets/m2-repair-runs-and-remounts.md`）：
  手动修补 `applied` → 12.3 秒后重挂完成（32/32）；定时臂 `applied` → 同回合内联
  挂载，登记的重挂复核为无事可做、不重复调用。
- 一次 `applied` 修补的总成本 = 修补调用 + 一次全量挂载调用（本课 32 节点，12–56
  秒，视契约门是否打回重试）。
- 与生长唤醒的互斥由挂载槽 `learning-mount-{course}` 串行保证：两者同时登记时，
  重挂做全量，生长唤醒在复核处判无事可做或只挂增量。
- 重挂失败只留痕（Failed 账本行），不重试：挂载保持失效，横幅提示手动「重新检
  查」，定时臂到点也会补挂。
