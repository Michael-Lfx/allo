## 〇、系统版本要求（重要前置）

MXC 对操作系统版本有**硬性门槛**，低于门槛的功能直接不可用。这不是配置问题，无法通过调整绕过。

### 我们的支持范围（Windows）

| 功能 | 最低系统版本 | 说明 |
|---|---|---|
| **基础隔离**（进程容器，我们本次测试用的） | **Windows 11 24H2（内部版本 26100）** | 低于此版本**此功能不可用** |
| 完整虚拟机隔离 | 同上，且需额外启用系统组件并重启 | 见附录 A |
| 独立用户隔离（最严格） | **版本 26340.9212 的 Insider 预览版** | 普通正式版**没有**，客户机器上基本不具备 |

**⇒ 直接结论：MXC 无法覆盖 Windows 10 用户，也无法覆盖 Windows 11 的 23H2 及更早版本。**
这部分用户的机器**不具备**使用 MXC 的前提条件。

### 官方标注的验证范围与我们的实测环境

| 项 | 官方标注 | 我们的实测环境 |
|---|---|---|
| Windows | Windows 11 24H2+（**官方在 25H2 上验证过**） | **Insider 29671**（比官方验证的版本更新） |
| 构建工具 | Rust 1.93（锁定版本）、Node.js ≥ 18 | 一致 |

**需要留意的两点：**

1. 我们跑在**更新的 Insider 预览版**上，而官方只保证在 25H2 上验证过。
   即我们测的是"超前版本"，**在正式版上的表现可能不同**。
2. 官方文档特别提供了一份"各版本 Windows 能强制哪些策略"的对照表
   （23H2 / 24H2 / 25H2 / 25H2+），**说明不同版本的系统，隔离能力本身就不一样**。
   这意味着**不能假设"同一个 MXC 在所有 Windows 上表现一致"**。

### 其他平台（供参考）

| 平台 | 最低系统要求 |
|---|---|
| Linux（x64 / ARM64） | 无版本门槛，但**需要系统预装对应运行时**（默认用 `bwrap`） |
| macOS（ARM64 / x64） | 无版本门槛，需配置格式 0.7.0-alpha 及以上 |

## 一、结论（先说结果）

> **技术上可行，但当前不适合作为生产环境的安全边界。**
> 建议：**先小范围试点，不整体切换。**

三句话概括：

1. **能跑通。** 我们让它实际跑了真实的编译、代码拉取、类型检查，全部成功，而且全程断网。
2. **但拦不住的关键问题有一个。** 它**拦截动作时会给出误导性提示**，我们的 Agent 会因此判断错方向。
3. **联网下载依赖走不通。** 用户机器上装了本地代理时，沙箱不允许访问本机自己的端口，实测**下载依赖失败 → Agent 任务失败**（详见 6.1）。
4. **系统版本门槛高，覆盖不了老用户。** 基础功能**要求 Windows 11 24H2 及以上**——
   **Windows 10 和 Windows 11 23H2 及更早的机器完全用不了**（详见第〇节）。

**补充说明：** 微软官方也明确写着"现阶段不应把任何 MXC 配置当作安全边界"。

**建议的下一步：** 先做零风险的观察性接入（3–5 天），同时并行解决代理问题；
不建议现在就承诺集成进产品。

## 二、这件事要解决什么问题

我们的 Agent 需要在本机执行命令（编译、测试、装依赖、发 PR）。这带来一个矛盾：

| 如果 | 后果 |
|---|---|
| 什么命令都放行 | Agent 可能误删文件、误改配置、把本机密钥发出去 |
| 每条命令都找人批准 | 人会被拖垮（业界实测：默认模式下用户会批准 **93%** 的弹窗，等于没拦） |

**业界公认的解法是"沙箱"**：给 Agent 一个受限的"笼子"——只能动指定的目录、不能联网——这样绝大多数动作不用问人，只有真正越界的才需要批准。据微软公布的数据，好的沙箱能把权限弹窗减少 **84%**。

**MXC 就是微软为此提供的官方方案**，今年 6 月开源（MIT 协议），能在 Windows / Linux / macOS 上用同一套配置实现隔离。对我们尤其重要的是：**我们目前唯一可用的沙箱只支持 macOS，而我们的主力平台是 Windows**——也就是说 Windows 用户现在处于"零隔离"状态。

**所以这次评估的核心问题是：MXC 能不能补上 Windows 这块空白。**

## 三、我们测了什么

测了 5 个关键问题 + 4 项补充验证 + 1 次端到端真实任务。用一句话说明每项：

| # | 测什么 | 结果 |
|---|---|---|
| 1 | 能不能挂到我们现有的进程管理上 | ✅ **能**（用我们真实代码验证，不是模拟） |
| 2 | 出问题时能不能定位到具体进程 | ⚠️ 只能定位到"外壳"，拿不到沙箱内的真实进程 |
| 3 | 强制结束时能不能清理干净 | ✅ **能**，零残留，且机制已查明 |
| 4 | 被拦截时错误信息是否可读 | ❌ **不可以**（核心问题，见下） |
| 5 | 有没有更省事的替代路径 | ⚠️ 有，但需要重启机器才能验证 |

**端到端实测（最关键的一次）：** 让沙箱运行我们仓库的真实命令，**全程断网**：

| 操作 | 结果 |
|---|---|
| 编译 Rust 代码（cargo build） | ✅ 成功，产物落盘 16 MB，真实编译 |
| 读取代码仓库（git） | ✅ 成功，读到 4555 条提交记录 |
| 前端类型检查（bun，耗时 72 秒） | ✅ 完整跑完，**速度与不用沙箱时几乎一致**（71.5 秒 vs 71.9 秒） |

**这一条是本次测试最有价值的结果**：证明日常开发中"编译 + 测试 + 检查"这一整类工作，**可以在完全断网的沙箱里正常完成**。

## 四、核心问题：错误信息会误导 Agent

这是唯一一条我认为**必须在接入前解决**的问题。

### 问题是什么

沙箱拦截一个动作时，Agent 看到的提示是这样的：

```
拒绝访问。(os error 5)
```

**问题在于：这句话对三种完全不同的情况长得一模一样。**

| 实际情况 | Agent 看到的 | Agent 会怎么想 |
|---|---|---|
| 文件目录没权限 | 拒绝访问 | 换个路径？ |
| **网络被沙箱禁止** | 拒绝访问 | 也去查文件权限？ |
| **依赖没下载（因为断网）** | 拒绝访问 | 也去查文件权限？ |

**注意第二种**：明明是"不让联网"，提示却是"拒绝访问"——**连"网络"两个字都没有**。
我们专门做了对照实验：把缓存目录改成可写之后，**报错一字不变**，证明确实来自网络限制而非文件权限。

### 为什么这很严重

Agent 是靠错误信息来决定下一步的。提示误导，它就会：

1. 反复尝试修改文件权限、换路径——**而我们都知道问题不在那儿**
2. 连试几次失败后，有的 Agent 会**谎报任务完成**，有的会**试图绕过限制**
3. 对我们的实际影响是：**消耗额外的对话轮次，然后失败**——也就是"能用但很笨"

**打个比方**：就像告诉一个修理工"门打不开"，但真实原因是"你被禁止出门"。他会一直研究锁，而问题根本不在于锁。

### 为什么不能等微软修

我们查了 MXC 的内部机制：它有一套"记录被拒操作"的功能，但**只记录权限类拒绝，不记录文件和网络类拒绝**。
我们已经把这个发现整理成可复现的缺陷，准备提交给微软。但**不能指望它短期内修好**。

**所以这一条需要我们自己在接入层做**——把"这次失败到底是什么原因"补上。这也是下面工作量估算里的第 1 项。

## 五、其他需要注意的点

### 5.1 隔离强度是"打折"的

沙箱要能让开发工具正常工作，就必须给它比较宽的读取权限。我们实测的策略需要开放"整盘可读"。

| 我们想要的 | 实际的 |
|---|---|
| 能编译，但读不到我的密钥文件 | **两件事做不到同时** |

原因是 Windows 上的 MXC **不支持"细粒度拒绝"**（比如"整盘可读，但屏蔽密钥目录"）。

**但这不等于不安全。** 因为**网络隔离是有效的**（我们实测确认）：Agent 能读到密钥文件，**但发不出去**。
所以最终防线是"断网"，而不是"不让读"。

**这个取舍需要明确知悉**：我们的安全模型建立在"网络隔离"这一个支点上，而不是多层防御。

### 5.2 两个"能用但别扭"的限制

| 限制 | 影响 |
|---|---|
| 沙箱内**不能杀进程**（`taskkill` 失败） | 测试工具如果靠杀进程清理，会失败 |
| 并发派生进程行为异常（12 个进程只有 8 个存活，随后全部退出） | 高度并行的测试（我们有约 15,900 个测试）可能受影响 |

这两点**尚未查清影响范围**，但我们明确标记了风险——因为"能编译"不等于"能跑测试"。

### 5.3 需要重启机器才能验证的替代方案

MXC 还有一条"长驻沙箱"的路子（把沙箱当一个长期服务，而不是每条命令包一层）。
这条路的优势是绕开上面所有进程管理问题，但本机缺一个 Windows 组件，**需要启用功能并重启机器**。
我没有擅自操作，列为待决事项。

## 六、风险一览（供决策）

**已确认的风险：7 项**（其中 1 项是好的——沙箱不残留垃圾文件，零泄漏）

**尚未验证的技术风险：8 项**，其中两项已在本轮查明（见下）。

### 6.1 联网场景：已测，发现一个**实际阻断**（重要）

**先说准确结论：请求要经过"宿主上的本机端口"时就会失败，与联网权限无关。**

**沙箱里的 `127.0.0.1` 不是宿主上的 `127.0.0.1`。**
沙箱有它**自己的回环接口**——所以同一个 `127.0.0.1`，在两边指向不同的地方：

| 谁 | `127.0.0.1` 指向 |
|---|---|
| 宿主上的代理软件 | **宿主的**回环接口 |
| 沙箱内运行的进程 | **沙箱自己的**回环接口 |

**⇒ 沙箱能连自己起的服务，但看不到宿主上的服务。**
（这与"端口被拦掉"不是一回事，见下面的对照。）

我们一开始以为"开一下联网权限就好了"，**实测证明不行**：

| 权限 | 管什么 | 我们的实测状态 |
|---|---|---|
| **出网权限** | 能不能访问外网 | ✅ **已经开着，而且有效** |
| **宿主回环权限** | 能不能连**宿主**上的本机端口 | ❌ **系统不支持这一档，无法打开** |

**实测证据（同一次运行，全部在"出网权限已开"的前提下）：**

| 探针 | 结果 |
|---|---|
| 直连外网（GitHub 接口） | ✅ 成功 |
| **连沙箱内自己起的 HTTP 服务** | ✅ **成功**（`http_200`） |
| **连宿主上的代理 `127.0.0.1:7890`** | ❌ **超时** |
| 经宿主代理访问外网 | ❌ 失败 |

**中间两行放在一起才是关键**：同一个 `127.0.0.1`，连沙箱自己的服务成功、连宿主的代理失败。
**所以不是"本机端口被整体拦掉"，而是"看不到宿主的回环"。**
这也是为什么用户会觉得奇怪——报错和"沙箱坏了"看起来一样，但实际是两个不同的网卡。

**而且无法通过配置打开** —— 我们试了"允许访问宿主本机端口"的开关（MXC 里叫 `hostLoopback`，
直译就是"宿主回环"），系统直接拒绝：

> 该选项需要更高版本的系统安全环境支持（当前不支持）

**这个开关的用途正是打通"沙箱回环 ↔ 宿主回环"**，它不可用，就意味着这个隔离无法绕过 ——
要改的是"两张网卡之间通不通"，不是"开个权限"。

### 根因：这是 Windows 的"回环隔离"机制，不是 MXC 的缺陷

查到 Windows 有一项**专门的安全设计**：AppContainer 类型的沙箱进程**默认不能访问
`127.0.0.1`**（即"回环隔离"，Loopback Restriction）。

**微软的设计初衷是安全**：如果允许沙箱进程随便访问本机端口，它就可能利用本机
开放的其他服务（例如各种本地管理接口）的漏洞，**反过来攻击宿主机、逃出沙箱**。
所以默认关掉。

**这解释了为什么"装了代理的机器上，某些应用会上不了网"** ——
这也是为什么很多代理软件会内置一个"UWP 回环豁免"的小工具。

**佐证：** 我们这台机器的**回环豁免列表原本是空的**，
正好解释了"宿主上的代理对普通程序有效、对沙箱进程无效"。

### 那能不能像豁免 UWP 应用那样豁免 MXC？—— 实测：不行

Windows 官方给了豁免命令 `CheckNetIsolation.exe`。我们用管理员权限试了：

```
CheckNetIsolation LoopbackExempt -a -n=<容器名>
→ 返回"完成"，豁免列表里也出现了对应条目
```

**但加了豁免之后，沙箱仍然连不上宿主** —— 宿主回环、宿主局域网地址都还是超时。

**原因是这个命令对 MXC 不适用**：

| | UWP / 商店应用 | MXC 的沙箱 |
|---|---|---|
| 身份类型 | **打包应用**（有包名） | **进程安全环境**（MXC 内部标记） |
| 沙箱配置的生命周期 | 常驻 | **用完即删**（我们实测：文件系统、注册表都查不到） |
| `CheckNetIsolation` 能否处理 | ✅ 能（按包名查表） | ❌ **不能**（列表里显示"未找到"） |

**⇒ `CheckNetIsolation` 是面向打包应用的工具，对 MXC 用不上。**

### 但 MXC 自己提供了等价开关 —— 只是这台机器不支持

MXC 有一个专门的设置项叫 `hostLoopback`（**宿主**回环），
**它就是"回环豁免"的官方等价物**，只是走 MXC 自己的机制而不是 `CheckNetIsolation`。

**我们试了打开它，系统直接拒绝**（见上面引用的报错）。
**而"回环豁免"和"这个开关"是仅有的两条正统路径，两条都不通。**

### 顺带修正一处我们自己的推测

我们早先猜"连不上宿主局域网地址是因为缺少某个网络权限位"。
**看到回环隔离这个机制后，这个说法不成立** —— 回环隔离是**独立于网络权限**的机制。
宿主局域网地址为什么也不通，**我们没有查出确切原因**，不排除是 MXC 自身的策略限制。
**这一条标记为未查清，不作为结论。**

### 这里要说清楚：不是"我们的问题"，是"用户机器配置导致 Agent 失败"

前面写的是"我们的开发流程依赖代理"，**这个描述不准确**。准确的因果是：

| 环节 | 说明 |
|---|---|
| **用户机器上装了代理软件** | 国内开发者的**普遍配置**（Clash / v2ray / 公司代理等），不是我们的特殊情况 |
| 代理监听在**宿主**的本机端口 | 例如 `127.0.0.1:7890` |
| 某些工具读取了代理设置 | git `http.proxy` 等是常见来源 |
| Agent 在沙箱内执行命令 | 该命令若被派往代理 → 连**宿主的**本机端口 → **沙箱看不到，失败** |
| **结果** | **该命令失败 → Agent 任务失败** |

**⇒ 决定成败的是"该请求有没有被派去走宿主上的本机代理"，不是"有没有联网权限"。**

**⚠️ 注意是"部分工具失败"，不是"全部失败"——这一点很重要**

同一个沙箱、同一次运行里：

| 工具 | 是否经过代理 | 结果 |
|---|---|---|
| `gh api`（直连外网） | 否 | ✅ **成功** |
| `cargo`（依赖下载） | 是（git `http.proxy` 接管） | ❌ **失败** |
| `bun install` | 大概率是 | ❌ 失败 |

**这个"部分好、部分坏"的表现形态会造成额外的困扰：**

- 用户看到"有时能用有时不能用"，难以归因
- **Agent 也不知道差别** —— 它不知道 `gh` 能用而 `cargo` 不能用，
  于是会**反复重试同一类操作**
- **报错信息还会误导**（见第四节）：Agent 看到的是"拒绝访问"，
  会以为是文件权限问题，转而往错方向改，而不是报告"网络不通"
- 报错里**没有"代理"两个字**，用户不会想到是自己的代理配置

**一句话：不是功能降级，是直接失败；用户什么都没做错，只是机器上装了代理。**

**受影响范围取决于用户机器配置，而我们无法列举：**

| 用户配置 | 是否会触发 |
|---|---|
| 装了本地代理 + 工具继承了代理设置 | ❌ **会失败** |
| 公司统一代理（非本机端口） | ⚠️ 视具体配置而定 |
| 直连上网 | ✅ 不受影响 |

**⇒ 沙箱能否正常工作，部分取决于用户机器配置。**
这类失败在用户侧很难归因，也很难让用户自行解决。

**可行的应对 —— 按"谁来做"分三类（这才是重点）：**

| 类别 | 做法 | 可行性 |
|---|---|---|
| **① 我们能主动做的** | 沙箱启动前**检测本机代理配置**，命中时给出明确提示（而不是让 Agent 撞上去）；或**明确适用范围**：需要联网拉依赖的场景不走沙箱 | ✅ **唯一可行的路径** |
| **② 需要用户配合的** | 把代理软件改成**监听局域网地址**（不用 `127.0.0.1`） | ❌ **已实测排除**：沙箱连宿主局域网地址同样超时（见上文） |
| **③ 用 Windows 官方豁免** | 用 `CheckNetIsolation` 给 MXC 加回环豁免 | ❌ **已实测排除**：该工具面向打包应用，对 MXC 的进程安全环境身份不适用 |
| **④ 用 MXC 自己的开关** | 打开 `hostLoopback`（宿主回环） | ❌ **本机系统不支持**该能力位 |
| **⑤ 需要等上游的** | 等 MXC/系统支持"宿主回环"这一档 | ⚠️ 时序不可控 |

**⇒ 五条路里，四条已实测排除，只剩①（我们自己的检测与提示）。**

**这不是"暂时没找到办法"，而是 Windows 的隔离设计所致**（见上文根因分析），
**不存在靠改配置绕过的路径**。

**这也直接支持一个产品形态结论：**
在用户存在本机代理配置的场景下，**沙箱只负责"编译与测试"，依赖安装留在沙箱外完成**。
这样既拿到了隔离收益，又避开了本机代理的坑。

### 6.2 完整构建：已测，但被上面的隔离问题挡住

测了两种：全部 Rust 代码编译检查（全工作区）、桌面端主程序构建。

**两者都在"下载依赖"这一步失败**，根本没进入编译阶段——原因就是 6.1 的宿主回环隔离。

作为对照，**在沙箱外**跑同样的全工作区编译检查：
**成功**，编译 **82 个模块**，耗时 **4 分 02 秒**，**零报错**。

**⇒ "我们最大的构建任务在沙箱内能不能扛住"无法回答**，必须先解决代理问题，
或改成"提前把所有依赖备好，然后断网构建"。

**顺带发现一个限制**：断网沙箱只能支撑"依赖已全部备好"的构建。
只要缺一个依赖，整个构建就停在下载环节（本次测试里只缺一个包 `rmcp` 就卡住了）。

**架构层面的缺口：5 项**（这些属于"接入"的工作，现在一行代码都没写）：

- 接入设计不存在
- 审批策略未定 —— **沙箱一强制，不在策略内的动作就真的被拦**，如果没有预先定义好审批规则，连编译都会弹窗要批准
- 微软上游成熟度（官方自陈"不应视为安全边界"）

## 七、建议

### 推荐方案：分三步走

| 阶段 | 做什么 | 工作量 | 风险 |
|---|---|---|---|
| **第一步（建议立即做）** | 接入 MXC 的"记录"功能，只观察不拦截，收集我们真实任务需要哪些权限 | 约 3–5 天 | **零风险**（不需要管理员权限，不影响现有行为） |
| **第二步** | 补齐"错误原因识别"，让 Agent 能分清"没权限 / 没联网 / 缺依赖" | 约 1–2 周 | 低 |
| **第三步** | 在**非交互、离线**场景试点（编译、测试、类型检查） | 约 1 周 | 低，可随时回退 |
| **并行推进** | **解决代理问题**（换局域网可达的代理，或验证"预热依赖后断网构建"） | 取决于网络方案 | — |

**三步之后**再决定是否扩大到日常开发。

**注意第二步和代理问题的关系**：即使代理问题解决了，
"错误原因识别"这一项**仍然必须做** —— 它是让 Agent 不跑偏的基础，与网络无关。

### 明确不建议

- ❌ **现在就集成进产品。** 微软自己说它不是安全边界。
- ❌ **在代理问题解决前，承诺"沙箱内能装依赖"。** 实测已证明：用户装了本地代理时做不到。
- ❌ **跳过第二步直接试点。** 错误信息误导会直接影响 Agent 的成功率。
- ❌ **把它当成"多层防御"。** 我们的安全最终只靠"网络隔离"一个支点，需要明确知悉。

### 需要拍板的三件事

| # | 事项 | 影响 |
|---|---|---|
| 1 | **是否接受"整盘可读"这个折扣**（换取工具链可用） | 决定安全模型的形态 |
| 2 | **是否授权启用 Windows 组件（Windows 沙箱）并重启机器**，以验证"长驻沙箱"方案 —— 组件名、启用命令与注意事项见**附录 A** | 决定是否有第二条技术路线 |
| 3 | **沙箱内无法使用 Python**（发行版打包方式导致，无解） | 需产品侧确认可接受 |

**另外建议知悉一项**：沙箱内"下载依赖"能力受限（见 6.1）。
**用户机器上装了本地代理时，Agent 在沙箱内的联网命令会失败**（不是降级，是失败）。
影响的是用户，不是我们的开发流程 —— 因此需要产品侧决定如何应对：

- 要么在沙箱启动前检测并提示
- 要么明确沙箱的适用范围：**可能需要"沙箱负责编译与测试，依赖安装仍在沙箱外完成"**

---

## 八、一句话总结

> **MXC 让我们第一次有可能在 Windows 上给 Agent 加上执行隔离，实测证明日常的编译与测试可以安全地关在沙箱里跑。**
> **但它现在还不是一道可靠的安全边界，有一个会误导 Agent 的缺陷必须由我们自己补上；而且用户机器上装了本地代理时，"联网下载依赖"会直接导致 Agent 失败。**
> **建议先花 3–5 天做零风险的观察性接入，同时解决代理问题，再决定是否继续投入。**

## 附录 A：关于需要启用的 Windows 组件

报告第六节提到"需要重启机器才能验证的替代方案"，这里说明是哪个组件、如何启用。

### A.1 是哪个组件

| 项 | 值 |
|---|---|
| **显示名称** | **Windows 沙箱**（Windows Sandbox） |
| **系统功能名** | `Containers-DisposableClientVM` |
| **类别** | Windows 可选功能（虚拟化类） |
| **作用** | 提供一个**一次性的轻量 Windows 虚拟机**，用完即弃 |

### A.2 当前状态（实测）

| 项 | 状态 | 说明 |
|---|---|---|
| 功能状态 | **未启用（Disabled）** | 需要主动开启 |
| 相关程序文件 | **不存在** | 功能没启用就不会安装这些文件 |
| 内存 | **31.4 GB** | 充足（微软建议给虚拟机预留至少 4 GB） |
| CPU | **16 核** | 充足 |
| 虚拟机监控程序 | **已就绪** | 系统已检测到 |
| 虚拟化固件 | ⚠️ **报告为"未启用"** | 见 A.4 注意事项 |

**⇒ 硬件条件本身是满足的，缺的只是"启用"这个动作。**

### A.3 如何启用（一条命令）

以**管理员身份**打开 PowerShell，执行：

```powershell
Enable-WindowsOptionalFeature -Online -FeatureName Containers-DisposableClientVM
```

执行后：

1. 系统会提示**重启电脑**（必须重启才生效）
2. 重启后 `C:\Windows\System32\WindowsSandbox.exe` 会出现
3. 验证是否成功：`Get-WindowsOptionalFeature -Online -FeatureName Containers-DisposableClientVM`
   —— `State` 应显示 `Enabled`

**如果要关闭（回退）：** 同一条命令把 `Enable` 换成 `Disable`，同样需要重启。

### A.4 注意事项

| # | 事项 | 说明 |
|---|---|---|
| 1 | **需要管理员权限** | 普通账号无法启用 |
| 2 | **需要重启** | 无法热生效 |
| 3 | **可能还需要改 BIOS** | 虚拟化固件报告为"未启用"。这个标志项在已运行于虚拟机监控程序之下的系统上可能不可靠，但**不能排除**需要在 BIOS/固件里打开虚拟化。**即不一定一次重启就能搞定** |
| 4 | **系统版本门槛** | 属于虚拟化类功能，同样受第〇节的版本要求约束 |
| 5 | **代价是"重"** | 每次执行都要起一个完整虚拟机，占用内存与磁盘 |

### A.5 为什么它值得关心 —— MXC 有两条技术路线

| | 路线一（我们测的） | 路线二（需启用该组件） |
|---|---|---|
| MXC 内部名 | `processcontainer` | `windows_sandbox` |
| 隔离方式 | 同一个 Windows 内的**受限进程** | 完整的 **Windows 虚拟机** |
| 需要该组件 | 不需要 | **需要启用** |
| 我们测出的进程管理问题 | ❌ 存在（杀不掉进程、并发异常） | ✅ **天然绕开** |
| 是否需额外开关 | 否 | 需加 `--experimental` 参数 |

**关键点：我们测出的那些"能用但别扭"的限制（杀不掉进程、12 个并发进程只剩 8 个），
都来自"在同一台系统里做隔离"这个前提。换成整台虚拟机，这些问题的成因就不存在了。**

### A.6 结论

**因此未擅自启用，列入待决事项。**

- 它**不阻塞**推荐方案的第一步和第二步（都不需要它）
- 它只影响"**有没有一条更省事的技术路线**"
- 它不是必需项：路线一（已实测可行）本身就能工作

**待决问题：** 是否授权启用该组件并重启机器，以验证路线二。
考虑到 A.4 第 3 条（可能还要改 BIOS），建议预留一次额外的重启时间。
