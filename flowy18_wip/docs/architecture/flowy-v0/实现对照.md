## 一、Router 怎么做归属判断

| | |
|---|---|
| **我们的做法** | **有状态的模型**，带着全局上下文判断；先走确定性快筛，只有「多 work ＋ 消息无引用」才调模型 |
| **对比方案 A** | 无状态分类器（每条消息独立判） |
| **对比方案 B** | 纯规则（关键词表、批内继承） |
| **为什么不用 A** | 实测：有上下文 **8/8**，无状态 **5/8**。同一句话在「刚才在聊 A」和「刚提过 B」下归属不同 |
| **为什么不用 B** | 实测 **7/10**，而且判错是**静默**的 —— 消息被吞掉，用户不知道 |
| **代价** | 每次判定一次模型调用（快筛命中可免） |
| **证据** | `证据.md` §11.12、§11.13、§11.7 |

## 二、Router 能干多少活

| | |
|---|---|
| **我们的做法** | **只派活、不 await、不碰任何 I/O**。判据是一条不变式：**一秒内回到可响应** |
| **对比方案** | Router 也执行任务（多数 agent 框架的做法：一个 loop 干所有事） |
| **为什么不用** | 实测：Router 里放一个 8 秒的工具，**用户说话要等 7500 ms**；只派活则 **0.1 ms**，差 7 万倍 |
| **一个推论** | 渲染、搜索、bsk 操作浏览器，**一个都不能进 Router** |
| **证据** | `证据.md` §11.16、`flowy-skeleton/router_block.py` |

## 三、能力清单怎么给模型

| | |
|---|---|
| **我们的做法** | **按 work 渲染**一份清单；整份预算 **20 000 字符**，单条描述 ≤ **250 字符**；**超预算整份降级**成「名字 ＋ 路径」 |
| **对比方案 A** | 全局一份清单，所有 work 共用 |
| **对比方案 B** | 全部塞进 system prompt |
| **为什么不用 A** | work 之间能力不共享。全局清单会让 A work 看到 B work 的能力，模型会去调不该有的工具 |
| **为什么不用 B** | 清单会长。**超预算时截断一半比整份缩短更难用** —— 一半完整一半残缺，模型分不清 |
| **每条必带路径** | 模型看得到名字不够，得能马上去读 |
| **证据** | 参照实现 ZCode `context/sections/skills.ts`；`最终方案.md` §3.5 |

## 四、插件贡献什么

| | |
|---|---|
| **我们的做法** | **声明「服务」，不声明「函数」**：`mcpServers` / `lspServers` / `channels` 是服务；`skills` / `commands` / `hooks` / `agents` 是行为扩展 |
| **对比方案** | 插件直接注册 tool（函数） |
| **为什么不用** | ① 换实现要改能力包 ② 同一个进程，崩了拖垮宿主 ③ 命名空间容易撞 |
| **命名空间** | 服务天然隔离：`plugin:名字:服务` |
| **一个硬事实** | 参照实现的插件清单里**没有 `tools` 字段**。想给新工具，只能写 MCP server 或 LSP server |
| **证据** | 参照实现 ZCode `PluginManifest`；`最终方案.md` §3.6 |

## 五、能力装给谁

| | |
|---|---|
| **我们的做法** | **嘴给 Router，手给 Work**：`channels` → Router；`skills` / `mcpServers` / `agents` → Work；`hooks` → 运行时横切 |
| **对比方案** | 全部跟着能力包走 / 全部给 Router |
| **为什么不全给 Work** | `channels` 跟着能力包走，Worker 就能自己对外发消息，**「Worker 绝不直接跟人说话」这条铁律当场破掉** |
| **为什么不全给 Router** | 渲染、搜索这些手给了 Router，就是第二条那个 7500 ms |
| **怎么强制** | 装载时按类型过滤，剥掉的记诊断上报到卡上。**不是「不许调」，是「没有可调的东西」** |
| **边界（必须说清）** | Worker 有 bash 时它能 curl。**这条只在「没有 shell」时是真隔离，有 shell 时只是约定** |
| **证据** | `最终方案.md` §5.19 |

## 六、核验的期望值从哪来

| | |
|---|---|
| **我们的做法** | **从需求抽出的信息点**来。Worker 的配方只决定「放在哪」，不决定「有没有」 |
| **对比方案** | 拿 Worker 交的配方当期望值 |
| **为什么不用** | 那就是**自己出题自己判卷**：Worker 少做一页，配方里也只有两页，照着一查全对 |
| **实测** | 同一份产物：用缩水配方核验 **`ok=true`、8/8 全对**；用完整需求核验 **`ok=false`、4 个 `ANCHOR_MISSING`** |
| **一句话** | **配方可以决定「放哪」，不能决定「有没有」** |
| **证据** | `证据.md` §11.18、`flowy-skeleton/verify_gap.py` |

## 七、核验分几层

| | |
|---|---|
| **我们的做法** | **三层**：L1 结构（页数/标题/必填段）→ L2 字段（三锚四码）→ L3 语义（对不对题） |
| **对比方案** | 只做字段核验 |
| **为什么不只用字段** | ① 少一页会被 `ANCHOR_MISSING` 糊住，看不出是少了一页 ② 标题形状不是 `F` 前缀，字段核验**根本不看它** ③ 值全对但答非所问，字段层永远发现不了 |
| **实测 L1** | 五种情况 **5/5** 全对 |
| **实测 L3** | 只改正文里的「华东→华南」，L1 过、L2 过、**只有 L3 拦住**；它甚至发现「上海」和「华南区」自相矛盾 |
| **误判率：三次校准** | v1 标签泄漏（0% 假的）、v2 标题污染（30% 假的）、**v3 干净：误判 0/10、漏判 1/10**。样本小（95% 上限 26%），**首版仍先只提示、灰度验证**（§11.24） |
| **L3 的三条约束** | 可否决不可放行 / fail-closed / 每条 issue 必须带依据 |
| **证据** | `证据.md` §11.19、§11.20、§11.21 |

## 八、核验不过怎么办

| | |
|---|---|
| **我们的做法** | **硬门**：核验报告 `ok=false` 就发不出去。三道检查：报告不存在 → 拒；`ok=false` → 拒；产物哈希对不上 → 拒 |
| **对比方案** | 出张卡写明「未通过」，人点「发」还是发了 |
| **为什么不用** | **核验如果允许人一键越过，它就只是一份建议** |
| **强行发怎么办** | 允许，但必须显式勾选「我知道核验没过」，记 `deliver_override`，**永久带标记不可消除** |
| **实测** | 核验失败后查事件日志：**一条 `deliver` 都没有**（skeleton 专用路径） |
| **普通入口** | 外部审查从普通入口走，得到 `verify(false) → branch → sign → deliver`。**所以还需要「唯一出入口」机制：别处根本拿不到发送器**（§6.4） |
| **wip 现状（2026-11-25）** | 初版 `4e35a1580` 仅对 `.pptx` 调只读 `gate.check()`；**现役 `5e96fb681` + `599b82c35` 已全面收口**：`publish_file` 全类型走 `DeliveryStore::deliver_with`（方案 A 显式豁免表 `EXEMPT_NO_VERIFIER_V0` + `deliver_intent → deliver / deliver_blocked` 审计落盘），Studio 渲染 §8.3 核验结论卡、未勾选禁点 Override 与聊天/资料库永久徽标（见 `证据.md` §11.27） |
| **验收方式** | **不是看提示文案，是查日志** —— 「被拒」很容易做成「提示拒绝、实际发出去了」 |
| **证据** | `证据.md` §11.16、`flowy-skeleton/main.py run-gate` |

## 九、验收器自己崩了怎么办

| | |
|---|---|
| **我们的做法** | **fail-closed** —— 验收器崩溃／超时／输出非法，一律判**不通过** |
| **对比方案** | fail-open（崩了当通过） |
| **为什么不用** | 实测：fail-open 在五种状态下只对 **2/5**，把「崩溃／超时／非法输出」三种都当成了通过 |
| **两家都踩过** | Claude Code：「hook 崩了动作照常放行，要显式配 `onFailure: block`」；ZCode：「其他失败、超时及非法输出会产生诊断，**不能当作可靠拒绝**」 |
| **证据** | `证据.md` §11.17、`flowy-skeleton/gate_failure.py` |

## 十、验收器能不能放行

| | |
|---|---|
| **我们的做法** | **可否决，不可放行**。放行仍要程序核验全过 |
| **对比方案** | 让 Router（一个 LLM）既验收又放行（卡兹克文章里的做法） |
| **为什么不用** | 它是 LLM，**会编理由**。让一个会编理由的东西掌握放行权是危险的；掌握否决权则安全 —— 多挡一次只是麻烦，多放一次才是事故 |
| **两个不对称** | 否决可以主观，**放行必须客观** |
| **证据** | `证据.md` §11.7（模型判断也会静默错） |

## 十一、打断怎么做

| | |
|---|---|
| **我们的做法** | `kill()` 之后**轮询确认进程真的退出了**，才改状态 |
| **对比方案** | `kill()` 返回就认为已经停了 |
| **为什么不用** | 实测：`kill()` 返回只用了 **5.62 ms**，但此刻 `poll()` 还是 `None`；**再轮询 17.8 ms（2 次）才确认退出** |
| **参照实现撞过同一个坑** | ZCode `topicContinuation.ts`：「必须等到指定 run 的**权威终态**；**停止 RPC 返回不等于运行已经结束**」 |
| **证据** | `证据.md` §11.15、`flowy-skeleton/main.py run-interrupt` |

## 十二、观测怎么做

| | |
|---|---|
| **我们的做法** | **只加一个字段** `root_session_id`；其余全部塞进 `ObservationEvent.payload`（本来就是 `serde_json::Value`） |
| **对比方案 A** | 上 OpenTelemetry / 自建 span 树 |
| **对比方案 B** | 提前定义一堆 `CostBasis` / `ToolTiming` 结构体 |
| **为什么不用 A** | 现有的 10 个业务 id 已经表达父子（`parent_execution_id` / `parent_model_call_id`），再加一套 trace/span 就是**两套真相** |
| **为什么不用 B** | 没有读方的字段全是负债 |
| **一条升级规则** | 只是记录 → 塞 payload；**需要按它查询/聚合** → 才升为正式字段 |
| **只有 `root_session_id` 需要升级** | 因为追查时要按它查 |
| **证据** | `最终方案.md` §13；`crates/agent/nomi-agent-trace` 已有 `payload: Value` |

## 十三、多 work 怎么并行

| | |
|---|---|
| **我们的做法** | N 个 work 各自持有产物、各自过三层核验、各自出一张卡 |
| **对比方案 A** | 一个会话里串行做 |
| **对比方案 B** | 一个任务拆成子步骤（agent team / subagent） |
| **为什么不 A** | 一件事卡住全卡住 |
| **为什么不 B** | 子步骤共用一个目标、一个产物。**我们要的是「多件事各自收束」** |
| **实测** | 三个 work：墙钟 **2.42 s**，串行 **6.51 s**；砍掉其中一个的一页，**另外两个结论未变** |
| **证据** | `证据.md` §11.21、`flowy-skeleton/e2e_three.py` |

## 十四、无来源的消息怎么受理

| | |
|---|---|
| **我们的做法** | **先受理、独立落盘，再判归属。** 快筛只认「有来源」：`from_work` / `reply_to_card` / `ref` 有值 |
| **对比方案** | 「当前只有一个活跃 work」也算快筛命中，直接归入（原定 100% 确定度） |
| **为什么不用** | A 正在跑时你在总输入框说「顺便把招聘计划也做了」—— 没有来源、没有引用，**候选唯一就会被错归进 A**。而错归会污染 A 的产物、记录和签字 |
| **降级后它还能干什么** | 问人时把那个唯一的活跃 work 当**默认选项**，但**不能自动归入** |
| **「先受理」为什么关键** | 不要因为归属没定就不接受输入。**B 必须能立刻拿到编号** —— 这正是第一张开发单要验的事 |
| **来源** | 外部审查发现；`最终方案.md` §2.4 / §2.5；`证据.md` §11.23 |

## 十五、工作终态、多件交付与崩溃恢复怎么判定（2026-11-25 · `feat/flowy-v0-rc`）

| | |
|---|---|
| **我们的做法** | **宿主掌控工作终态**：① `SessionRecord` 持久化版本化 `WorkContract`（跨修订继承必交项/页数/关键事实）；② 每轮按 `submission_id` 独立落 `SubmissionOutcome`（`Completed / Partial { missing } / Failed / Aborted`）；③ 交付审计改两阶段（`stage_with` 落 `deliver_intent`，真正写入 `ArtifactStore` 可见 marker 后才 `confirm_delivered` 落 `deliver`）；④ 崩溃恢复仅在 `SubmissionOutcome::Completed` 且交付组 marker 全可见时才补写回执 `Completed` |
| **对比方案 A** | 模型正常 `end_turn` 即判 `Completed`，每轮只从最新一句 prompt 重建简报契约 |
| **对比方案 B** | `publish_file` 暂存时直接写 `deliver` 审计；重启看到会话里有助手回复就判已完成 |
| **为什么不用 A** | 反例实测：要求三件齐交但 PPT 核验失败时，另外两件入库后整轮仍被误标 `Completed`；第二轮说「只改日期」时丢失首轮页数与报价约束 |
| **为什么不用 B** | 反例实测：暂存未提交时审计已多出 `deliver` 而资料库可见数为 0；`Error` 会话带失败助手回复重启后被误恢复成 `Completed`（0 产物） |
| **统一查询口径** | `work_status(work_id)` + `session_work_status(session_id)`，重启前后对同一个工作编号给出同一答案（日志 / 会话 / 资料库三处一致） |
| **证据** | `证据.md` §11.30；提交 `45d0d317b` / `54d10087f` / `a0e96262b` / `65772f857` |

## 十六、队列调度、死信重试与 UI 怎么解耦（2026-11-25 · `feat/flowy-v0-rc`）

| | |
|---|---|
| **我们的做法** | **内核自治 + `6+4` 强类型控制契约**：`set_autonomous_drain(true)` 由宿主 Tokio runtime 自治排水（`apply_config` 就绪自动唤醒）；`visible_acceptances()` 暴露全部非 `Completed`/非 `Cancelled` 回执（含退避中 `Retrying`、`Dead`、`Quarantined`）；`cancel_task(TaskTarget)` / `apply_card_action(CardAction)` / `prepare_shutdown()` 显式传目标 ID，绝不读 UI `active`；`RetryDeadReceipt` 持锁原子追加新 `Accepted` + 原 ID `Superseded`（映射 `Cancelled` 退出列表） |
| **对比方案 A** | UI 定时器轮询 `pending_acceptances()` 并手动调 `run_accepted_once()` / `finish_accepted()` |
| **对比方案 B** | `RetryDeadReceipt` 只追加新回执、保留旧死信为 `Dead` |
| **为什么不用 A** | `pending_acceptances()` 会过滤退避期/死信/隔离态导致任务从 UI 凭空消失；UI 轮询逻辑与调度耦合，易在切会话或启动竞态时串台 |
| **为什么不用 B** | 配合 `visible_acceptances()` 后，旧死信会在重启后「诈尸」重新出现，重复点击会复制任务 |
| **证据** | `证据.md` §11.30；提交 `71cdb8e92` / `65772f857` |

## 十三、Structured Outputs 怎么过生产网关

| | |
|---|---|
| **我们的做法** | **单次 HTTP + 单类型化工具调用（`tools` + `tool_choice` 强制点名，不附带 `strict` 字段）**，经 `Model::sampling_params` 透传，失败时自动降级纯 JSON 文本解析 + 宿主 `Value::Bool` 严格校验 |
| **对比方案 A** | `response_format: { type: "json_object" }` |
| **对比方案 B** | `response_format: { type: "json_schema", strict: true }` |
| **为什么不用 A** | 生产网关实测（`server.flowyaipc.com` / `AIPC-qwen3.8-flash`）直接返回 **HTTP 500 Internal Server Error** |
| **为什么不用 B** | 生产网关实测思考模型被压扁为 `{"issues": [], "ok": false}`（空问题列表），触发宿主 fail-closed `Inconclusive` |
| **实测收益** | 单次 HTTP 提取工具入参，真云端 L3 从纯文本 `16.76s` 降至 **`5.14s`（提速 3.26×）**，冲突样本 `7.16s` 精准抓出全部 2 项问题 |
| **证据** | `证据.md` §11.31；提交 `f47804a9d` |

## 十四、跨平台取消回收与执行沙箱怎么分层

| | |
|---|---|
| **我们的做法** | **复用 `rpi-tools` 已有跨平台进程树强杀（Windows `win32job::Job` + Unix `process_group(0)`）**，集中修复 `RunFence` 两阶段取消回收锁（`RunTicket` RAII + `Condvar` + `PublishToken`）；在 `flowy-agent-core` 落地 100% MIT 净室 `shell_policy.rs` + `sandbox.rs`（诚实上报 `Degraded`，预留 macOS Seatbelt / Linux `bwrap` 纯构造器） |
| **对比方案 A** | 在 `flowy-agent-core` 外层再包一层 Windows Job Object |
| **对比方案 B** | 直接拷贝外部开源实现（如 `zed/crates/sandbox`）或在无真机下硬启用 `Enforced` |
| **为什么不用 A** | `rpi-tools` 已绑 Job Object，外层套壳冗余且解决不了「取消后未等退出即放行新轮次」的跨平台竞态 |
| **为什么不用 B** | `zed` 为 `GPL-3.0-or-later` 与 `flowy18_wip`（MIT）协议冲突；未在对应 OS 真机实测逃逸阻断前虚报 `Enforced` 比诚实报 `Degraded` 更危险 |
| **证据** | `跨平台沙箱与进程回收预留方案.md`、`证据.md` §11.31；提交 `a3fc4214a` / `13dad5e4c` |

3. **每个新增字段必须有现在就读它的调用方。**
4. **能被 `payload` 装下的，不加字段。**
