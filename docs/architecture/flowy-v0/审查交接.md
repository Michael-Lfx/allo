## 四、我主动交代的洞

按严重程度排。**这些不是留给审查者去发现的，是我已知的。**

### 洞 1｜全部验证都在 Python 骨架，零 Rust

12 个脚本没有一行调用 Flowy 代码。模拟的 vs 真实的：

| 模拟的 | 真实的 |
| --- | --- |
| 自己写的假 loop | `agent_loop.rs:343` |
| `queue.Queue` | `steering` 队列 |
| jsonl 事件 | `nomi-agent-trace` schema |
| 打印的「卡」 | GPUI 卡片 |
| 线程池 | 多会话隔离 |

**所以：验证的是「约束有没有道理」，不是「架构在 Flowy 里能不能跑」。**

### 洞 2｜一秒不变式是模拟的

我给 Router 塞了一个 `time.sleep(8)` 来模拟慢工具，证明「阻塞就等于用户等」。

**但没在真 pi-rust 里跑过一个真慢工具。** 真 loop 的行为（尤其是 `steering` 队列在工具批次期间的表现）没验过。

### 洞 3｜样本量小

| 实验 | 样本 |
| --- | --- |
| §11.12 有状态 vs 无状态 | 各 1 轮，8 条消息 |
| §11.22 L3 误判率 | 10 对，20 次调用 |
| §11.21 多 work | 3 个 work，跑 1 次 |

**8/8 和 5/8 的差距，样本量撑不住统计显著性。** 只能说「方向一致」。

### 洞 4｜没有真实用户场景

所有测试都是我造的数据。**没有一条是「真人拿真需求用它，觉得比不用好」。**

而且我造的数据本身出过两次问题（§11.20、§11.22 都有记录）—— **说明我造样本的水平不足以支撑「已验证」的说法。**

### 洞 5｜§5.19 的装载规则在 Worker 有 bash 时失效

文档自己写了：Worker 有 shell 就能 curl，所以「拿不到渠道句柄」只是约定不是隔离。

**这是设计上承认的妥协，不是疏漏。但审查者应该判断这个妥协能不能接受。**

### 洞 6｜推演冒充过结论的地方

- §11.7 的原始结论（「程序化硬规则失败」）后来被收窄成「程序化决策失败」，**原结论下得太宽**。
- §13 观测那节，我是读了 `nomi-agent-trace` 源码推出来的，**没跑过一次真写入**。

## 五、给审查者的检查清单

按性价比排。**前三条最可能有收获。**

### ① 假绿检查（最重要）

`证据.md` §11.15 记录过一次**假绿**：故障注入因为字段名写错（`slides[].value` vs 真实的 `pages[].text`）而静默没生效，链路「通过」了但什么都没注入。

**同样的错法可能还在别处。** 建议：

- 打开 `flowy-skeleton/struct_test.py` 和 `l3_test.py`，看每个用例**是不是真的造出了它声称的缺陷**
- 特别看 `e2e_three.py` 的隔离性测试：砍掉一页之后，是不是真的砍掉了

### ② 对照是否公平

`§11.18`（期望值来源）的对照：一份产物用「缩水配方」验 → True；用「完整需求」验 → False。

**检查点：这两次用的是同一个 check.py、同一份产物吗？** 如果是，结论成立；如果有别的差别，结论要打折。

### ③ 三层核验是否重叠

L1 结构、L2 字段、L3 语义。**有没有一种缺陷会被两层同时判定为失败，导致「三层」实际只有两层？**

§11.19 的用例里，「少一页」同时触发了 `SLIDE_COUNT_MISMATCH` 和 `SLIDE_MISSING` —— 这本身没问题，但要看有没有跨层重叠。

### ④ 文档自相矛盾

2021 行的方案，我查到过一处矛盾（§2.4「默认沿用」vs §5.15「默认不猜」），已经改掉。

**建议抽查：** §3.5 的清单预算（20000）与 §7.4 的上下文预算是不是同一个数；§6.4 的硬门与 §8.3 的卡片选项是否一致。

### ⑤ 代码预算是否够

V0 估 ~200 行（`ExecInput` + serde + round-trip + `root_session_id` + 三层核验调用点）。

**200 行能不能装下 `ExecInput` 的五条硬约束？（见 `最终方案.md` §4）** 这是需要判断的。

## 八、复核结果（2026-11-23 审查返回后补）

**结论：可以开始开发。** 但以下几处被推翻，已全部修正。

| 被推翻的 | 真实情况 | 修正位置 |
| --- | --- | --- |
| 「每个数都对」 | 新增一个**未声明**的文本框写同口径数字，L1/L2/L3 全过 —— 核验只认预先声明的字段 | `§6.7` 承诺收窄；`一页纸.md` 同步 |
| 「核验不过就拒绝」 | 从**普通入口**走，得到 `verify(false) → branch → sign → deliver`；换附件后旧报告仍被接受 | `§6.4` 补「唯一出入口」机制 |
| L3「0% 误判」 | **标签泄漏**：样本标题写了 `C01 good`，进了裁判正文。改中性标题后又因**标题与主题不匹配**制造了假误判（30%）。**第三次（标题取自简报主题）才是干净的：误判 0/10、漏判 1/10** | `§11.22` 作废、`§11.24` 记录三轮；L3 首版仍只出提示，50 次灰度后再定 |
| `bool()` 强转 | `bool("false")` 是 `True`，模型返回字符串就会被判通过 | `check_semantic.py` 改严格类型校验 |
| 路由规则 | §2.4「无来源不猜」vs §2.5 快筛③「唯一活跃 work → 100% 归入」，只有 A 活跃时 B 会被错归 | **已改**：快筛③ 降级为弱提示，不再自动归入；无来源消息**先受理、独立落盘，再判归属**（§2.5） |
| 「loop 同步」 | `await` 不阻塞线程。真实原因是 **loop 串行** | `§5.1` 机制已改正 |

**还有一条更重要的：这轮暴露的不是三个 bug，是同一个方法论问题。**

> **我测的全是「我想到的那条路」。**

## 九、给开发的第一张单子（审查建议，我认同）

**只验一件用户能感知的事：**

> A 还在跑慢工具时，我能提交 B、拿到编号，重开客户端还能找到 B。

四个时点分别记录：点击提交 ／ 本地事务提交 ／ 界面显示编号 ／ 模型首答。

再补三种情况：云端离线、双击提交、拿到编号后立即重启。

**这样才能分清「一秒内受理」和「一秒内给出语义答复」各自做到了多少。**

单独完成 `ExecInput` 序列化往返，**不足以验收这条纵线**。

**三项暂缓放行**（审查建议，我同意）：自动归入已有工作、L3 裁决产物是否合格、署名外发。
