# CHANGELOG 格式示例

这是**格式说明**，不是发版记录。真正维护的文件是仓库根目录
[`CHANGELOG.md`](../../CHANGELOG.md)。不要把本文的示例条目复制进去。

面向用户的变更怎么记，见 [`CONTRIBUTING.zh-CN.md`](../../CONTRIBUTING.zh-CN.md)
「Changelog 与 release notes」。自动更新如何抽取这段文字，见
[`BUILD_RELEASE.zh-CN.md`](../../BUILD_RELEASE.zh-CN.md)。

## 这个文件解决什么

| 你想知道的 | 答案 |
| --- | --- |
| 写在哪 | 只写根目录 `CHANGELOG.md` |
| 日常 PR 写哪 | `## Unreleased` 下面加一条 |
| 发版时写哪 | 把 Unreleased 收成 `## vX.Y.Z - YYYY-MM-DD` |
| 更新弹窗显示哪 | 该版本标题下面、下一个 `##` 之前的全部正文 |
| 不写能不能打包 | 能。OTA 也能推。弹窗会变成 `Flowy vX.Y.Z` 或误用上一个已发布版本 |

## 骨架（带标注）

下面是一份**假数据**骨架。注释只出现在本示例里，真实 `CHANGELOG.md` 不要写这些说明行。

```markdown
# Changelog                          ← 文件标题，仓库里已经有，不要改

一段简短说明。                         ← 可选。现有文件里有一段 pre-1.0 说明。

## Unreleased                        ← 必须一直留着。开发中的条目只往这里加。
                                     ← 标题不能带版本号。make:latest 会跳过这一节。

- 修了切换会话后粘贴纯文本重复插入。   ← 日常 PR：一条用户能看懂的短句。
- 首页设置页布局更稳定。

## v0.0.4 - 2026-08-18               ← 发版标题。必须包含 Cargo.toml 里的版本号
                                     ← （这里是 0.0.4）。日期建议有，抽取时不强制。

- 修了 Windows/Linux 标题栏拖拽。     ← 用户能感知的变化，一条一事。
- 联网搜索冷启动更不容易提前失败。
- **破坏性变更**：对外伙伴改为客服。  ← 有破坏才写。没有就整条删掉。
  旧配置不会自动迁移。
- 打包说明：本次只发 Windows。        ← 桌面 OTA / 安装包差异才写。没有就删。

## v0.3.3 - 2026-07-30               ← 历史版本。只追加、不改旧节含义。
```

## 每一段代表什么

| 部分 | 必须？ | 代表什么 |
| --- | --- | --- |
| `# Changelog` | 文件里已有 | 文档标题 |
| `## Unreleased` | **日常必须保留** | 还没打进某个版本的条目。打 tag 前把内容搬走，这一节留空即可 |
| `## vX.Y.Z - YYYY-MM-DD` | **发版时必须** | 这一节就是该版本的更新说明。`X.Y.Z` 必须能在标题里找到（与根目录 `Cargo.toml` 的 `[workspace.package].version` 一致） |
| 普通 `-` 条目 | 该版本有用户可见变化时要有 | 功能、行为变化、用户能感知的 bugfix |
| `**破坏性变更**` / `**BREAKING**` | 有破坏才写 | 用户要动手迁移的配置、数据、API、工作流 |
| `打包说明` / `Packaging note` | 桌面发版建议写 | 只发了哪个平台、签名/SmartScreen、已知安装限制 |
| 安全相关条目 | 有才写 | 用户或运营需要知道的安全修复/收紧 |
| 已知限制 | 有才写 | 这次发出版本明确做不到、或故意不修的点 |

版本标题**不要**写成 `## Unreleased 0.0.4` 或 `## 更新说明`。抽取逻辑只认：

1. 行以 `##` 开头；
2. 该行包含当前版本字符串（例如 `0.0.4`）；
3. 不是 `## Unreleased`。

找不到匹配标题时，会退到**第一个非 Unreleased 的 `##` 小节**——也就是上一个已发布版本，文案会错。

## 必须填到什么程度

分三档。**打包本身不检查 changelog。**

### 档 0 — 能打包、能 OTA（最低，弹窗可能是错的）

什么都不写也可以。`make:latest` 会按顺序用：

1. 你手动传的 `--notes` / `--notes-file`（CI 默认不传）
2. 同版本旧清单里的 `notes`
3. `CHANGELOG.md` 匹配小节
4. 再没有就写成 `Flowy vX.Y.Z`

### 档 1 — 更新弹窗显示「这一版」的说明（OTA 最低正确档）

发版前 `CHANGELOG.md` 里至少有：

```markdown
## v0.0.4 - 2026-08-18

- 一句话说明用户能感知的变化。
```

要求：

- 标题包含版本号，且版本号等于这次要打的 tag / `Cargo.toml` version；
- 标题下面至少有一段非空正文（一条 bullet 就够）；
- 日常积累的条目不要留在 `## Unreleased` 就去打 tag，否则弹窗抽不到它们。

### 档 2 — 公开发版建议写全（仓库政策）

有则写、没有就省略，不必凑栏目：

1. 用户能感知的功能 / 行为 / bugfix（几条短句，不要把 Unreleased 长文原样搬上去）
2. 破坏性配置、数据、API、工作流（必须写清楚「用户要做什么」）
3. 安全相关变化
4. 打包 / updater 说明（只发了哪个平台、签名情况）
5. 已知限制

够不够的判断：**给用户看 10 秒能知道「要不要更、更完要不要手动迁移」**。不是给代码评审看实现细节。

## 一条怎么写

| | 写法 |
| --- | --- |
| 长度 | 一两句。弹窗会展示整节正文，不要把实现过程写进去 |
| 主语 | 用户看到的结果（「修了粘贴重复」），不要写文件名、PR 号、内部模块 |
| 一条一事 | 不要一条里塞五个子系统 |
| 语言 | 真实 `CHANGELOG.md` 目前是英文；弹窗原文照显示。中英文都可以，但同一节保持一种语言 |
| 不要写 | commit 列表、`feat:` 前缀、函数名、测试名、评审讨论 |

**太细（不要这样）：**

```markdown
- AutoWork/IDMM: bypass-model (sidecar) decisions with confidence below 0.4
  now fall back to the conservative rule action. Previously the floor was 0.0.
```

**够用（可以这样）：**

```markdown
- AutoWork 在低置信度时改走保守规则，不再直接套用旁路模型的结论。
```

## 发版时怎么搬 Unreleased

1. 确认 `Cargo.toml` 版本，例如 `0.0.4`。
2. 在 `## Unreleased` **下面**插入 `## v0.0.4 - 2026-08-18`。
3. 把准备随这个版本发出去的条目移到新标题下，改成短句。
4. `## Unreleased` 留空（或只留下一版才发的条目）。
5. 再打平台 tag，例如 `v0.4.2-windows`。tag 里的 `X.Y.Z` 必须和这一节标题、Cargo 版本一致。

CI 的 `make:latest` 不会把 `## Unreleased` 写进 `latest.json`。
