# 技术方案写作规范 (Technical Solution Specification Standard)

> **定位**：Flowy / Agent Store 体系技术方案与架构设计文档的统一编写标准与质量红线。  
> **适用范围**：`docs/` 及各子目录（如 `docs/agent-store/`、`docs/architecture/`）下所有技术方案、架构决策（ADR）、重构规格及实施计划文档。  
> **一句话原则**：**“前置易懂架构，后置完整底稿；图表语法严谨，权衡验收闭环。”**

---

## 1. 核心宗旨与分层架构

技术文档是工程团队跨角色协作、代码演进与质量审计的第一生产力。过去部分文档容易陷入两个极端：要么是零散代码与技术术语的无序陈列，缺乏脉络；要么在重构优化时过度精简，导致底层契约与历史证据丢失。

本规范确立**“易懂方案正文 + 完整历史底稿”**的双层归档模型：

```text
┌──────────────────────────────────────────────────────────────┐
│ 1. 易懂技术方案正文 (文档前半部分，通读 5 分钟掌握全局)       │
│   ├── §1 背景与核心痛点 (业务定位、现状问题剖析、能力对比矩阵) │
│   ├── §2 方案全景与架构设计 (Mermaid 拓扑图、核心原则与边界)   │
│   ├── §3 核心设计与模块规范 (模块交互、时序图、数据结构、状态机)│
│   ├── §4 关键决策与权衡矩阵 (ADR 决策项、选定方案与放弃理由)   │
│   └── §5 验收标准与验证矩阵 (TC 测试用例、断言口径、验证梯子)   │
├──────────────────────────────────────────────────────────────┤
│ 2. 附录：原始技术底稿与历史归档 (文档后半部分，供审计与追溯) │
│   > 归档说明：完整保留重构前的原始底稿、字段级细节与讨论记录  │
│   [100% 逐字保留重构前的历史全文，严禁以概括代全文造成删除]  │
└──────────────────────────────────────────────────────────────┘
```

## 2. 方案正文标准结构 (六大核心模块)

一份合格的技术方案文档必须按照以下结构依序展开：

### 2.1 标题与元数据头部 (Header)
```markdown
# [功能 / 模块名称] · 技术方案

> **状态**：🧊 架构基线 / ✅ 已实现 / 🔧 部分实现 / 📋 计划 / 🗄️ 历史
> **核心原则**：[1~2 句话提炼本方案的最高设计不变量与架构准则]
```

### 2.2 第一节：背景与核心痛点 (Background & Pain Points)
- **业务背景**：说明功能面向谁、解决什么业务场景；
- **现状与三大痛点**：以清晰的编号条目列出当前实现的具体阻断点（性能瓶颈、概念混淆、安全漏洞或接口缺失）；
- **能力对比矩阵**：使用 Markdown 表格，对比“现状行为”与“本方案目标”，直观反映演进价值。

### 2.3 第二节：方案全景与架构设计 (Architecture & Topology)
- **端到端拓扑图**：使用 Mermaid `flowchart TD` 或 `flowchart LR` 呈现清晰的系统边界（外部 Client、App Server 宿主、上游引擎/外部服务等 Subgraph 分层）；
- **核心目标 vs. 明确的非目标**：清晰界定本阶段“做什么”与“坚决不做什么”，防止范围蔓延；
- **架构不变量**：如“凭据不出宿主”、“有效权限取交集”等安全红线。

### 2.4 第三节：核心设计与模块规范 (Subsystem Design)
- **模块职责划分**：分小节阐述各子模块、服务与提供者的详细职责；
- **交互时序流**：涉及多端或多步骤异步交互时，必须配以 Mermaid `sequenceDiagram`（带 `autonumber` 与明确角色）；
- **数据结构与契约**：给出关键的 Rust Struct、TypeScript Interface 或 JSON-RPC API Schema（注明字段类型、是否可选与脱敏要求）；
- **状态机矩阵**：若存在生命周期，必须列出完整合法状态枚举、状态迁移前置条件与不可逆终态。

### 2.5 第四节：关键决策与权衡矩阵 (Decision & Trade-off Matrix)
必须包含表格，详细记录技术选型过程中的取舍，避免后续无休止重议：

| 编号 | 决策点 | 选定方案 | 放弃的替代方案与理由 |
|---|---|---|---|
| **D1** | [决策项名称] | **[最终采纳的结论]** | ❌ [备选方案名称]：[具体技术缺陷、安全隐患或维护成本高昂的原因] |

### 2.6 第五节：验收标准与验证矩阵 (Acceptance Criteria & Ladder)
- **验收用例表 (TC / Criteria)**：每一项都具备独立编号（如 `S1`, `TC-AS-001`）、清晰的操作路径及可断言的验收结果；
- **验证梯子 (Verification Ladder)**：列出从快速单元测试到端到端集成的最小验证执行顺序。

## 3. Mermaid 图表规范与跨端渲染防坑指南

在 VS Code、GitHub 及 WebUI 中，Mermaid 渲染引擎对语法和拓扑有严格的解析限制。任何语法瑕疵都会导致整个代码块直接崩溃回退为纯文本。**编写 Mermaid 时必须遵守以下硬性规范：**

### 3.1 语法严禁项 (Critical Syntax Invariants)

1. **Flowchart 中严禁使用 `-->>` 箭头**：
   - ❌ **错误**：`A -->> B`（`-->>` 属于 `sequenceDiagram` 专有语法，flowchart 会直接报解析语法错误）；
   - ✅ **正确**：使用实线箭头 `-->`、虚线箭头 `-.->` 或粗线箭头 `==>`。
2. **连接线文本含特殊符号必须双引号包裹**：
   - ❌ **错误**：`A -->|1. skill/files & skill/file| B`（`&` 是 Mermaid 节点合并操作符，会导致语法树断裂）；
   - ❌ **错误**：`A -->|call(name, args)| B`（括号与逗号会导致解析混淆）；
   - ✅ **正确**：`A -->|"1. skill/files 与 skill/file"| B` 或 `A -->|"2. connector/call(name, args)"| B`。
3. **判断节点 `{}` 严禁内嵌中括号 `[]`**：
   - ❌ **错误**：`Gate{"[connector_proxy] 是否开启"}`（`[` 与 `]` 会与矩形节点定界符产生语法冲突）；
   - ✅ **正确**：`Gate{"策略门禁: connector_proxy 是否开启"}`。
4. **多行换行一律使用 `<br/>`，严禁使用 `\n`**：
   - ❌ **错误**：`Node["第一行\n第二行"]`（`\n` 会被原样作为字符输出甚至触发转义异常）；
   - ✅ **正确**：`Node["第一行<br/>第二行"]`。

### 3.2 架构语义与数据流拓扑规则

1. **数据流向必须符合真实网络与代理拓扑**：
   - 在代理架构（Proxy）中，上游进程（如 Stdio 子进程、外部 HTTP 服务）严禁直接反向连回外部客户端（Client）；
   - 响应数据流必须经由宿主路由器/适配器完成校验、凭据剥离与脱敏后，统一回传客户端。
2. **避免跨多层嵌套子图（Subgraph）的反向回连**：
   - 避免从内层子图跨越三四层父级子图逆向拉长连线，这会导致 Dagre 排版引擎计算重叠交叉线，引发渲染畸变；
   - 复杂调用推荐“上层总览拓扑用 Flowchart，底层详细调用时序用 SequenceDiagram”。

## 4. 历史底稿保护与 Git 变更原则

在对既有技术文档进行易懂性重构与演进时，必须严格遵守以下原则：

1. **底稿 100% 完整归档，严禁以概括代全文**：
   - 重构文档时，正文上方撰写易懂架构；正文末尾必须添加：
     ```markdown
     ---

     ## 附录：原始技术底稿与历史归档 (Historical & Technical Reference Archive)

     > **归档说明**：以下完整保留重构前的原始技术底稿、历次讨论与历史记录全文，供历史追溯、协议字段详细对照与技术审计。

     ---

     [原文档全部内容逐字无损贴回]
     ```
   - 严禁在附录中写入类似 `（此处保留原 §4.1...）` 的占位符，严禁擅自删减原始参数表、历史会议纪要和排期记录。
2. **Git Diff 自查准则**：
   - 提交重构 PR 前，必须执行 `git diff --stat <path>` 自查；
   - 理想的重构结果应当是**大幅正向新增 (Insertions >> 0)，删除行极小或为 0 (Deletions ≈ 0)**。如果出现上千行内容被删，说明历史底稿发生泄露或遗失，必须立刻检出恢复并重新注入附录。
3. **不可变链接格式**：
   - 文档内互相引用的路径，一律使用 GitHub 标准相对路径或包含 `file:///` 的绝对安全路径（如 `[05-protocol](docs/agent-store/05-flowy-agent-store-app-server-protocol.md)`）；
   - 代码符号与字段名强制反引号包裹，保持高对比度与易读性。
