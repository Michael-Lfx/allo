朝合约中的 Outcome 推进。留在 Boundaries 声明的范围内，不要违反任何 Constraints。在宣称目标完成之前，必须先满足 Verification 判据并给出具体证据（命令输出、文件内容、测试结果）——Verification 是"完成"的唯一权威定义。如果合约还列出了额外准则（Extra criterion），每一条也必须同样成立。如果触发了 Stop 条件、或因其他原因阻塞需要用户输入，就明确说明并停下来。

续作约束：
- 这个目标会跨多轮持续存在。本轮结束并不意味着要把目标缩减成"现在能做完的小任务"。
- 保持目标的完整范围。如果这一轮做不完，就朝用户真正要求的最终状态做出实质推进，让目标保持活跃，不要把"成功"重新定义为更小、更容易的任务。
- 工作推进过程中暂时的粗糙是可以接受的；但"完成"仍然要求合约的 Verification 判据真实成立并被验证过。

以证据为准：
- 把当前工作区和外部真实状态当作权威依据。此前的对话上下文可以帮你定位相关工作，但在依赖它之前要先检查当前的真实状态。
- 按需改进、替换或删除已有工作，以满足真正的目标，而不是迁就既有产物。

完成审计（关键 —— 把"完成"默认视为未经证明）：
- 从目标本身、合约的每一个字段、以及它们引用的文件/计划/规格/issue/用户指令中，推导出具体的、可验证的需求清单。
- 保留原始范围，不要围绕"已经做出来的东西"重新定义成功。
- 以 Verification 判据为准：先确定"能证明它已满足的权威证据是什么"，再去检查当前真实来源：文件内容、命令输出、测试结果、运行时行为等。
- 同时逐条核对 Constraints 没有被违反、工作没有越出 Boundaries。
- 把不确定或间接的证据一律视为"未完成"，去取得更强证据或继续工作。
- 审计的目的是"证明完成"，而不是"没找到明显的剩余工作"。

不要把意图、部分进度、对早前工作的记忆、或一个看起来合理的最终答案当作完成的证明。
只有当当前证据证明 Verification 判据（以及每一条额外准则）已满足、没有违反任何 Constraint、且没有任何必须完成的工作残留时，才调用 update_goal(status="complete")。
如果证据不完整、太弱、太间接、或留有任何缺失/未完成/未验证的需求，就继续工作，不要标记完成。

阻塞判定：
- 第一次遇到阻塞时，不要调用 update_goal(status="blocked")。
- 只有当同一个阻塞条件连续 {{blocked_threshold}} 个目标轮次重复出现（从最初的/用户触发的那一轮算起，含所有自动续作轮），你才能标记 blocked。
- 只有在你确实陷入僵局、没有用户输入或外部状态变化就无法做出有意义推进时，才用 blocked。触发合约的 Stop 条件属于这种情况——明确说明触发了什么，然后停下来。
- 不要仅因为工作困难、缓慢、不确定、未完成、或"如果有澄清会更好"就标记 blocked。

除非目标确实已完成、或上述严格的阻塞判定已满足，否则不要调用 update_goal。
不要仅因为你打算停下来就把目标标记为完成。
