结论

技术上可行，但当前不适合作为生产环境的安全边界
建议：先小范围试点，不整体切换。先做零风险的观察性接入（3 至 5 天），同时并行解决代理问题。

✓能跑通

真实的编译、代码拉取、类型检查，全程断网全部成功。

✕有一个必须解决的问题

拦截动作时给出误导性提示，Agent 会判断错方向。

✕联网下载依赖走不通

用户机器上装了本地代理时，下载依赖直接失败，Agent 任务失败。

✕覆盖不了老用户

基础功能要求 Windows 11 24H2 及以上，Windows 10 与 23H2 及更早完全用不了。

补充：微软官方亦明确写着「现阶段不应把任何 MXC 配置当作安全边界」。

前置条件 · 系统版本

系统版本是硬门槛，不是配置问题

能力最低系统版本
基础隔离（本次测试所用）Windows 11 24H2（内部版本 26100）
完整虚拟机隔离同上，且需额外启用系统组件并重启
独立用户隔离（最严格）版本 26340.9212 的 Insider 预览版，普通正式版没有
MXC 无法覆盖 Windows 10 用户，也无法覆盖 Windows 11 的 23H2 及更早版本。 这部分用户的机器不具备使用前提，且无法通过调整配置绕过。

需留意：我们跑在 Insider 29671（比官方验证的 25H2 更新），官方自己也为各版本 Windows 提供了「能强制哪些策略」的对照表，说明不能假设同一个 MXC 在所有 Windows 上表现一致。

结论一

真实开发任务在沙箱里跑通了，而且全程断网

让沙箱运行我们仓库的真实命令，编译、拉代码、类型检查全部成功，速度与不用沙箱几乎一致。

✓编译 Rust 代码
16 MB
cargo build 成功，产物真实落盘
✓读取代码仓库
4555
git 成功读到的提交记录条数
✓前端类型检查
72.0 s
bun 完整跑完，宿主上为 71.5 s
这意味着：日常开发中「编译 + 测试 + 检查」这一整类工作，可以在完全断网的沙箱里正常完成。 隔离收益是真实可拿到的。

这也是本次测试最有价值的结果：它证明 MXC 的隔离强度足以支撑真实开发，而不是只能跑玩具示例。

结论二 · 唯一必须在接入前解决的问题

「拒绝访问」四个字，盖住了三种完全不同的原因

拒绝访问。(os error 5)

实际情况Agent 看到的Agent 会怎么做
文件目录没权限拒绝访问换个路径
网络被沙箱禁止拒绝访问也去查文件权限
依赖没下载（因为断网）拒绝访问也去查文件权限
后果：Agent 会反复去查文件权限、换路径，而问题根本不在那儿；试几次失败后，有的会谎报任务完成，有的会试图绕过限制。 实测影响是消耗额外对话轮次，然后失败。

这一条必须由我们自己在接入层补上：MXC 现有的「记录被拒操作」功能只覆盖权限类拒绝，不覆盖文件与网络类拒绝，短期不会修好。

结论三

两个取舍，接入前需要明确知悉

取舍一：能编译，但读不到我的密钥

Windows 上的 MXC 不支持「细粒度拒绝」，实测的策略需要开放「整盘可读」。
好在网络隔离是有效的：Agent 能读到密钥文件，但发不出去。

取舍二：能编译，不等于能跑测试

沙箱内不能杀进程（taskkill 失败）；并发派生进程异常（12 个进程只有 8 个存活）。
我们有约 15,900 个测试，影响范围尚未查清。

需要拍板的第一件事就是取舍一：是否接受「整盘可读」这个折扣，以换取工具链可用。这决定了安全模型的形态。
由此得出的关键判断：我们的安全最终只建立在「网络隔离」这一个支点上，不是多层防御。这一点必须明确知悉。

结论四 · 影响用户，不是影响我们

用户机器上装了本地代理，沙箱内下载依赖会直接失败

用户机器装了代理软件（Clash / v2ray / 公司代理），这是国内开发者的普遍配置
代理监听在宿主的本机端口，例如 127.0.0.1:7890
某些工具读取了代理设置，例如 git http.proxy
命令被派往代理，即去连宿主的本机端口，而沙箱看不到它
结果该命令失败，Agent 任务失败
与联网权限无关。出网权限已经开着而且有效；缺的是「宿主回环」这一档权限，而本机系统不支持这一档，无法打开。 沙箱有它自己的 127.0.0.1，所以它能连自己起的服务，但看不到宿主上的服务。
是「部分工具失败」，不是全部失败。同一次运行里：gh api 成功（不经过代理），cargo 与 bun install 失败（被代理接管）。 用户会看到「有时能用有时不能用」，难以归因，报错里也没有「代理」两个字。

根因

是 Windows 的回环隔离，不是 MXC 的缺陷

Windows 有一项专门的安全设计：AppContainer 类型的沙箱进程默认不能访问 127.0.0.1。 设计初衷是安全：如果允许沙箱随便访问本机端口，它就可能利用本机开放服务的漏洞，反过来攻击宿主机、逃出沙箱。

仅有的两条正统豁免路径，实测都不通

路径结果
Windows 官方豁免：CheckNetIsolation
✕命令返回「完成」、列表里也出现了条目，但沙箱仍然连不上宿主。该工具面向打包应用，对 MXC 的「进程安全环境」身份不适用（列表里显示「未找到」）。
MXC 自己的等价开关：hostLoopback
✕系统直接拒绝：该选项需要更高版本的系统安全环境支持（当前不支持）。
结论：这不是「暂时没找到办法」，而是 Windows 的隔离设计所致。 要改的是「两张网卡之间通不通」，不存在靠改配置绕过的路径。

应对

五条路里，四条已实测排除，只剩我们自己检测提示

路径做法结论
① 我们主动做沙箱启动前检测本机代理配置，命中时给出明确提示，而不是让 Agent 撞上去
✓唯一可行
② 让用户改代理把代理软件改成监听局域网地址（不用 127.0.0.1）
✕实测排除：连局域网地址同样超时
③ Windows 官方豁免用 CheckNetIsolation 给 MXC 加回环豁免
✕实测排除：该工具对 MXC 身份不适用
④ MXC 自己的开关打开 hostLoopback（宿主回环）
✕本机系统不支持该能力位
⑤ 等上游支持等 MXC / 系统支持「宿主回环」这一档
!时序不可控
由此得出一个产品形态结论：在用户存在本机代理配置的场景下， 沙箱只负责「编译与测试」，依赖安装留在沙箱外完成。这样既拿到隔离收益，又避开本机代理的坑。

建议

分三步走，三步之后再决定是否扩大

阶段做什么工作量风险
第一步（建议立即做） 接入 MXC 的「记录」功能，只观察不拦截，摸清真实任务需要哪些权限 约 3 至 5 天
✓零风险
第二步 补齐「错误原因识别」，让 Agent 能分清「没权限 / 没联网 / 缺依赖」 约 1 至 2 周
✓低
第三步 在非交互、离线场景试点（编译、测试、类型检查） 约 1 周
✓低，可随时回退
并行推进 解决代理问题（换局域网可达的代理，或验证「预热依赖后断网构建」） 取决于网络方案
!待定
注意：即使代理问题解决了，「错误原因识别」这一项仍然必须做。它是让 Agent 不跑偏的基础，与网络无关。

边界与决策

明确不建议的四件事，以及需要拍板的三件事

明确不建议

现在就集成进产品。微软自己说它不是安全边界。

承诺「沙箱内能装依赖」。实测已证明：用户装了本地代理时做不到。

跳过第二步直接试点。错误信息误导会直接影响 Agent 成功率。

把它当成多层次防御。安全最终只靠「网络隔离」一个支点。

需要拍板

1. 是否接受「整盘可读」这个折扣，以换取工具链可用。这决定了安全模型的形态。

2. 是否授权启用 Windows 沙箱组件并重启机器，以验证「长驻沙箱」这条替代路线。详见下页。

3. 沙箱内无法使用 Python（发行版打包方式导致，无解）。需产品侧确认可接受。

另外建议知悉：用户机器上装了本地代理时，Agent 在沙箱内的联网命令会失败，影响的是用户而不是我们的开发流程，因此需要产品侧决定如何应对。

一句话总结

MXC 让我们第一次有可能在 Windows 上给 Agent 加上执行隔离，实测证明日常的编译与测试可以安全地关在沙箱里跑。
但它现在还不是一道可靠的安全边界：有一个会误导 Agent 的缺陷必须由我们自己补上； 而且用户机器上装了本地代理时，「联网下载依赖」会直接导致 Agent 失败。
建议先花 3 至 5 天做零风险的观察性接入，同时解决代理问题，再决定是否继续投入。

待决事项

是否启用 Windows 沙箱组件，以验证第二条技术路线

MXC 有两条技术路线。我们测的是路线一（受限进程）；路线二用完整虚拟机，天然绕开我们测出的所有进程管理问题， 但需要启用一个 Windows 组件并重启机器。我没有擅自操作。

路线一（已测）路线二（需启用组件）
隔离方式同一个 Windows 内的受限进程完整的 Windows 虚拟机
我们测出的进程管理问题
✕存在（杀不掉进程、并发异常）
✓天然绕开
当前状态已实测可行未启用，硬件条件已满足（内存 31.4 GB、16 核）
启用方式：管理员身份执行 Enable-WindowsOptionalFeature -Online -FeatureName Containers-DisposableClientVM， 必须重启才生效。可能还需要改 BIOS，不一定一次重启就能搞定，建议预留额外时间。

它不是必需项：路线一本身已能工作，也不阻塞推荐方案的前两步。它只影响「有没有一条更省事的技术路线」。
